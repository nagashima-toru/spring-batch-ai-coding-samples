# 基本設計 Skill

要件定義書を入力に、ジョブ分割・方式選定・IF設計・テーブル設計を行い基本設計書を作成する。
**方式判断は必ず `docs/architecture.md`（方式設計書＝SSoT）に準拠する。**

## 入力と出力（工程連鎖）

| | 内容 |
|---|---|
| 入力 | `docs/projects/{案件名}/requirements.md`（前工程 `/requirements` の成果物） |
| 参照 | `docs/architecture.md`（方式設計書）、`batch-sample/docs/`（パターン別の選定基準） |
| 出力 | `docs/projects/{案件名}/basic-design.md`（テンプレート: `templates/basic-design-template.md`） |
| 次工程 | `/detail-design` がジョブ単位でこの成果物を入力とする。完成後 `/review-design` でレビューする |

## 進め方

1. 要件定義書を読み、未確定事項が設計に影響しないか確認する（影響する場合はユーザーへ確認）
2. **ジョブ分割**: 実行タイミング・リラン単位・依存関係が異なるものは別ジョブにする
3. **方式選定**: ジョブごとに Chunk / Tasklet / Flow を選定する
   - 判断基準は `docs/architecture.md` §3.1 の表に従う
   - 類似パターンのサンプル（`batch-sample/docs/` の「選ぶべき場面/選ばない場面」）を根拠として引用する
4. **IF設計**: ファイル・APIのレイアウト、ジョブパラメータを定義する
5. **テーブル設計**: 業務テーブル（app スキーマ）の追加・変更を定義する
6. ジョブID（`{案件略号}-{連番3桁}` 例: `SALES-001`）とジョブ名（命名規約 §11）を採番する

## 設計判断で必ず記載すること

- 各ジョブの方式選定の**理由**（「なぜ Chunk か」を書く。結論だけ書かない）
- リラン設計: リスタート再開か最初から再実行か、冪等性の担保方法（UPSERT/洗い替え）
- エラー処理: Skip 対象（業務エラー）と即時異常終了（システムエラー）の分類、Skip 上限
- 終了コードと運用アクション（0/2/1。architecture.md §7 の規約から変えない）
- 概算処理時間とチャンクサイズの初期値（根拠となる件数規模を添える）

## 禁止事項

- `docs/architecture.md` に反する方式の採用（必要なら先に方式設計書の改訂を提案する）
- 命名規約（architecture.md §11）に従わないジョブ名・Step名
- 根拠のない方式選定（サンプルの選定基準・件数規模を根拠として示すこと）
