# 要件定義 Skill

バッチシステムの要件をヒアリング・整理し、後続の基本設計の入力となる要件定義書を作成する。

## 入力と出力（工程連鎖）

| | 内容 |
|---|---|
| 入力 | ユーザーへのヒアリング内容、既存資料（現行仕様書・運用手順・データ仕様など） |
| 出力 | `docs/projects/{案件名}/requirements.md`（テンプレート: `templates/requirements-template.md`） |
| 次工程 | `/basic-design` がこの成果物を入力とする |

案件名はユーザーに確認し、英小文字ケバブケース（例: `sales-import`）とする。

## 進め方

1. **既存資料の確認**: 提示された資料を読み、判明している事実と不明点を分離する
2. **ヒアリング**: 以下の観点で不明点を質問する（一度に3〜5問まで。まとめて聞きすぎない）
3. **要件定義書の作成**: テンプレートに落とし込み、不明点は「未確定」と明記して残す
4. **確認**: ユーザーへ要約を提示し、認識齟齬がないか確認する

## ヒアリング観点

### 業務要件
- このバッチは何の業務のどの部分を自動化するのか（背景・目的）
- 入力データはどこから来るか（システム・部門・フォーマット・文字コード・件数規模）
- 出力は何をどこへ渡すか（テーブル・ファイル・API、後続の利用者）
- データの加工・変換・集計ルール（計算式・コード変換・丸め）
- 入力データが不正な場合の業務上の扱い（後回しにできるか、全件停止すべきか）

### 実行条件
- 実行タイミング（日次/月次/随時、時刻、締め処理との関係）
- 先行・後続ジョブとの依存関係
- 処理時間の制約（何時までに終わる必要があるか）
- 実行単位（全件/差分、対象日付の指定方法）

### 非機能・運用要件
- データ量（現在と将来の件数、増加傾向）
- リラン要件（失敗時に誰がどう再実行するか、途中再開の要否）
- 監視・通知要件（失敗を誰がどう検知するか）
- 保持期間（入力ファイルの退避、エラーレコードの扱い）
- セキュリティ（個人情報の有無、マスキング要否）

## 判断の指針

- 方式（Chunk/Tasklet 等）はこの工程では決めない（基本設計の責務）
- ただし方式選定に影響する事実（件数規模・リラン要件・依存関係）は必ず確定させる
- 「未確定」が残ったまま次工程へ進む場合は、要件定義書の未確定一覧に理由と確認先を書く
