# 一気通貫パイプライン Skill

`docs/projects/{案件名}/requirements.md` が確定している状態から、PR作成までの全工程を
既存Skill（`basic-design` 〜 `system-test`）に委譲しながら自動的に進める。

**このSkill自身は設計判断をしない。** 各工程の実体は対応する `.claude/skills/{skill}/SKILL.md`
であり、本Skillの役割は「どの工程を・誰に（どのモデルのサブエージェントに）・どの順で・
どこまで自動で流すか」を制御することに限定する。

## 対象範囲

- **入力**: `docs/projects/{案件名}/requirements.md`（既に存在し、内容が確定していること）
- **スコープ外**: `/requirements`（要件のヒアリングは対話が必須なため、本Skill実行前に主エージェントが
  別途完了させておく。requirements.md が無い、または**設計判断に影響する**未確定事項が残っている場合は
  開始しない。要件定義書の §「未確定事項」に解決時期が「基本設計まで」等と明記され、後続工程で確定させる
  前提のものは対象外とし、該当工程のサブエージェントに確定させる）
- **出力**: 基本設計書〜システムテスト実施記録一式、実装コード、PR

## 実行方針（モデル・実行主体）

| 工程 | 実行主体 | モデル | 理由 |
|---|---|---|---|
| 基本設計（`basic-design`） | Agentサブエージェント | **Opus** | ジョブ分割・方式選定に推論が必要 |
| 設計レビュー（`review-design`、基本設計対象） | Agentサブエージェント | **Opus** | レビューは必ずサブエージェント＋Opusで実行する |
| 詳細設計（`detail-design`、ジョブごと） | Agentサブエージェント | **Opus** | Step設計・エラー処理設計に推論が必要 |
| 設計レビュー（`review-design`、詳細設計対象） | Agentサブエージェント | **Opus** | 同上 |
| 実装（`implementation`） | Agentサブエージェント | **Sonnet** | 設計書どおりに実装する作業系タスク |
| 単体テスト（`unit-test`） | Agentサブエージェント | **Sonnet** | 作業系タスク |
| 結合テスト（`integration-test`） | Agentサブエージェント | **Sonnet** | 作業系タスク（Docker必須） |
| コードレビュー（`review-code`） | Agentサブエージェント | **Opus** | レビューは必ずサブエージェント＋Opusで実行する |
| システムテスト（`system-test`） | Agentサブエージェント | **Sonnet** | 作業系タスク（Docker必須） |
| PR作成（コミット・プッシュ・`gh pr create`） | **主エージェント本人**（委譲しない） | - | git push・PR作成は他者に見える／取り消しにくい操作のため、作業系サブエージェントへは委譲せず主エージェントが直接行う |

サブエージェントは `subagent_type` に `general-purpose` を指定し、モデルは上表のものを
`model` パラメータで明示する。

「作業系はSonnet優先」の原則だが、Sonnetサブエージェントが検証ループの早期エスカレーション条件
（同一エラーが2ラウンド連続で解消しない。`docs/development-guide.md` §5.3）に達した場合は、
そこで打ち切らず**Opusサブエージェントへ切り替えて再試行**する（推論が必要な局面への昇格）。
**昇格は1回まで・昇格後は最大2ラウンド**とし、それでも解消しない場合は主エージェントが引き取り、
§「停止して確認するタイミング」に従う（通算の上限を超えて回し続けない）。

## 進め方

1. **事前確認（すべて満たすまで次に進まない）**:
   - `docs/projects/{案件名}/requirements.md` が存在し、ステータスが「確定」であること。
     未確定事項が残っている場合は、それが設計判断を左右するかを判定する（解決時期が後続工程に
     設定されているものは想定内として進め、設計判断に影響するものは停止してユーザーへ依頼する）
   - `git status` がクリーンであること（無関係な未コミット・未追跡の変更があれば停止して確認する。
     手順10のコミットが巻き込むため）
   - `main` から feature ブランチを切る（`development-guide.md` §3。設計書・コードの生成を
     `main` 上で始めない）
   - `docker info` が成功すること（結合テスト・システムテストの前提。未起動ならユーザーへ起動を
     依頼して停止する。`integration-test` SKILL.md 手順1）
   - `git rev-parse HEAD` で起点コミットを控える（手順10でコミット対象を特定するため）
2. 以下を**順番に**実行する（並列化しない。後続工程が前工程の成果物に依存し、複数ジョブでも
   共有テーブル・IFの整合を取る必要があるため。`development-guide.md` §2.1 の工程フローに従う）。
3. 各工程は Agent ツールで起動する。サブエージェントへのプロンプトには必ず以下を含める:
   - 対象の `.claude/skills/{skill}/SKILL.md`（および参照する `templates/`・`references/`）を
     読んで指示どおりに実行すること
   - 入力ファイルの絶対パス（前工程の成果物）
   - その工程の検証ループ（該当Skill・development-guide.md §5 に規定されたもの）を
     実際に実行し、成功するまで（上限内で）繰り返すこと
   - **サブエージェントはユーザーに質問できない**。委譲先Skillが「ユーザーへ確認・合意」を
     求めている箇所は §「委譲先Skillの記述を上書きする点」に従い、独断で決めずに報告へ含めること
   - 完了時に以下を簡潔に返すこと: ①成果物パス ②検証結果（コマンドと結果） ③レビュー工程では
     指摘の区分別件数と対応内容 ④未確定・要確認事項（`[Ask]` を含む） ⑤設計書を改訂した場合はその内容
4. **基本設計→レビュー**:
   - `basic-design` サブエージェント（Opus）で `basic-design.md` を作成
   - `review-design` サブエージェント（Opus）で `basic-design.md` をレビューし、
     **[Must]/[Should] は全てそのサブエージェント自身が即座に修正まで行う**
     （指摘を返すだけで終わらせない。§「レビュー指摘の扱い」参照）
   - `[Ask]`（設計意図の確認）が残った場合のみ、主エージェントが受け取ってユーザーに確認する
5. **詳細設計→レビュー（ジョブごとに繰り返す）**: 基本設計書のジョブ一覧に載っている各ジョブIDについて、
   `detail-design` → `review-design` を4と同様の手順（Opus、指摘は自己修正）で実行する
6. **実装〜結合テスト（ジョブごとに繰り返す）**: `implementation` → `unit-test` → `integration-test`
   をジョブごとに Sonnet サブエージェントで実行する（各Skillが規定する検証ループを含む）。
   プロンプトには「詳細設計書は手順5でレビュー済みである」ことを明記する
   （`implementation` SKILL.md 手順1 のレビュー済み確認をサブエージェントが判断できないため）
7. **コードレビュー**: 対象パッケージ（実装したジョブ全体）に対して `review-code` サブエージェント（Opus）
   を実行し、指摘を**全て自己修正**したうえで `./mvnw clean verify` が通ることまで確認させる
8. **システムテスト**: `system-test` サブエージェント（Sonnet）でシナリオ作成・実施・記録まで行う。
   外部依存などでローカル実施が不可能なシナリオがある場合は、そのサブエージェントの結果を見て
   主エージェントがユーザーへ判断を仰ぐ（§「停止して確認するタイミング」）
9. **最終検証**: 主エージェント自身が `./mvnw clean verify` を1回通す（`development-guide.md` §3 手順3・
   実装 PR 用テンプレートのセルフチェック欄）。システムテストで追加したデータ生成スクリプト等を含めた
   最終状態で通ることを確認する
10. **PR作成**: 主エージェントが直接、コミット・プッシュ・`gh pr create` を実施する
    （ブランチは手順1で作成済み。GitHub Flow は `development-guide.md` §3）。
    - コミット対象は、手順1の起点コミット以降に**パイプラインが生成・変更したファイルのみ**に限定する
      （`git add -A` で無関係な変更を巻き込まない）
    - 本文は実装 PR 用テンプレート（`.github/PULL_REQUEST_TEMPLATE/implementation.md`）の見出しに沿って書き、
      設計 PR 用テンプレート（`design.md`）のセルフチェックと設計レビューの実施記録も含める（設計と実装を1つの PR に
      するため。`development-guide.md` §3）。設計書リンク・セルフチェック欄・レビュー実施記録（各工程の報告③を集約）を埋める
    - 本Skillの起動をPR作成の承認とみなすため、ユーザーに実行可否を尋ねない
11. 最後に、実行した全工程・各工程の検証結果・PRリンクを簡潔にまとめて報告する

## レビュー指摘の扱い（重要）

- `review-design` / `review-code` サブエージェントは、検出した **[Must]・[Should]（両Skillが定義する
  区分）の指摘を必ずその場で修正する**。「反映してよいか」をユーザーに尋ねるステップは挟まない
  （細かい指摘でも全て対応する、という方針のため）
- **[Ask]**（設計意図・業務判断の確認）は性質が異なる。答えを誤ると手戻りになるため、
  サブエージェントは修正せず「確認事項」として持ち帰らせ、主エージェントが
  `AskUserQuestion` でユーザーに確認してから該当箇所を反映する
- 指摘を修正したら、そのサブエージェント自身の中で再度ビルド・テストを実行し、
  デグレがないことを確認してから完了報告させる

## 委譲先Skillの記述を上書きする点

各Skillは単体（対話的）実行を前提に「ユーザーへ確認・合意」を求める箇所がある。パイプライン実行時は
サブエージェントがユーザーに問えないため、以下のとおり読み替える。**この読み替えは手順3の
プロンプトで明示的に伝える**（該当Skill側にも例外条項を記載済み）。

| 委譲先Skillの記述 | パイプライン実行時の扱い |
|---|---|
| `review-design` 手順4「ユーザーの了承を得て設計書へ反映する」 | [Must]/[Should] は了承取得なしで自己修正し、指摘一覧と修正内容を報告する。[Ask] のみ返す |
| `review-code` 手順4「修正はユーザー了承後」 | 同上（修正後 `./mvnw clean verify` まで通す） |
| `unit-test` 手順3「テストケース表をユーザーに提示してから実装する」 | 提示先を主エージェントとし、テストケース表を完了報告に含めたうえで実装まで進める |
| `system-test` 手順1「シナリオ一覧を…ユーザーと合意する」 | 同様にシナリオ一覧を完了報告に含めたうえで、実施・記録まで進める |
| `implementation` 手順1「未レビューならユーザーへ確認」 | 手順5でレビュー済みであることを主エージェントがプロンプトで保証する |
| `basic-design` 手順1「未確定事項…影響する場合はユーザーへ確認」 | 影響ありと判断したら作業を止め、確認事項として主エージェントへ返す |

## 停止して確認するタイミング

デフォルトは「確認なしで最後まで進める」。ただし以下は**手戻りにつながる**ため、必ず一度止めて
主エージェントが `AskUserQuestion` でユーザーに確認する。

- 事前確認（手順1）が満たせない場合（requirements.md が無い、設計判断に影響する未確定事項が残っている、
  作業ツリーに無関係な変更がある、Docker 未起動）
- 要件定義書の「未確定事項」が設計判断に影響する場合（本来はSkill開始前に解消済みのはずだが、
  基本設計・詳細設計サブエージェントが新たな未確定・矛盾を発見した場合を含む）
- 各設計工程で `[Ask]` 区分の指摘が残った場合（上記）
- 検証ループがOpusへ昇格しても解消しない場合（`development-guide.md` §5.3 の早期エスカレーション）
- システムテストのシナリオが外部依存等でローカル実施できない場合
- 破壊的操作が必要になった場合（既存データの削除、Flyway適用済みファイルの変更が必要と判明した等）

上記に該当しない限り、PR作成まで自動で進めてよい。

## 禁止事項

- 事前確認（手順1）を省略して工程を開始しない（特に feature ブランチ未作成のまま `main` 上で
  設計書・コードを生成しない）
- 工程の順序を入れ替えたり、レビュー工程を省略したりしない
- レビュー指摘の「対応不要」判断をサブエージェント・主エージェントの独断で行わない
  （[Must]/[Should] は修正、[Ask] は必ずユーザーに確認）
- 検証ループを通すために検証自体を弱める（カバレッジ閾値変更・テスト削除等）ことは、
  各工程のSkill定義同様に禁止（`development-guide.md` §5.4）
- PR作成（git push・`gh pr create`）をサブエージェントへ委譲しない
- `git add -A` 等でパイプラインの成果物以外の変更をコミットに含めない
