# 一気通貫パイプライン Skill

`docs/projects/{案件名}/requirements.md` が確定している状態から、PR作成までの全工程を
既存Skill（`basic-design` 〜 `system-test`）に委譲しながら自動的に進める。

**このSkill自身は設計判断をしない。** 各工程の実体は対応する `.claude/skills/{skill}/SKILL.md`
であり、本Skillの役割は「どの工程を・誰に（どのモデルのサブエージェントに）・どの順で・
どこまで自動で流すか」を制御することに限定する。

## 対象範囲

- **入力**: `docs/projects/{案件名}/requirements.md`（既に存在し、内容が確定していること）
- **スコープ外**: `/requirements`（要件のヒアリングは対話が必須なため、本Skill実行前に主エージェントが
  別途完了させておく。requirements.md が無い、または「未確定事項」が残ったままの場合は開始しない）
- **出力**: 基本設計書〜システムテスト実施記録一式、実装コード、PR

## 実行方針（モデル・実行主体）

| 工程 | 実行主体 | モデル | 理由 |
|---|---|---|---|
| 基本設計（`basic-design`） | Agentサブエージェント | **Opus** | ジョブ分割・方式選定に推論が必要 |
| 設計レビュー（`review-design`、基本設計対象） | Agentサブエージェント | **Opus** | レビューは必ずサブエージェント＋Opusで実行する |
| 詳細設計（`detail-design`、ジョブごと） | Agentサブエージェント | **Opus** | Step設計・エラー処理設計に推論が必要 |
| 設計レビュー（`review-design`、詳細設計対象） | Agentサブエージェント | **Opus** | 同上 |
| 実装（`implementation`） | Agentサブエージェント | **Sonnet** | 設計書どおりに実装する作業系タスク |
| 単体テスト（`unit-test`） | Agentサブエージェント | **Sonnet** | 作業系タスク |
| 結合テスト（`integration-test`） | Agentサブエージェント | **Sonnet** | 作業系タスク（Docker必須） |
| コードレビュー（`review-code`） | Agentサブエージェント | **Opus** | レビューは必ずサブエージェント＋Opusで実行する |
| システムテスト（`system-test`） | Agentサブエージェント | **Sonnet** | 作業系タスク（Docker必須） |
| PR作成（ブランチ・コミット・プッシュ・`gh pr create`） | **主エージェント本人**（委譲しない） | - | git push・PR作成は他者に見える／取り消しにくい操作のため、作業系サブエージェントへは委譲せず主エージェントが直接行う |

「作業系はSonnet優先」の原則だが、Sonnetサブエージェントが検証ループ
（`docs/development-guide.md` §5）の上限（同一エラー2ラウンド連続）に達して解消できない場合は、
そこで打ち切らず**Opusサブエージェントへ切り替えて再試行**する（推論が必要な局面への昇格）。
それでも解決しない場合は主エージェントが引き取り、§「停止して確認するタイミング」に従う。

## 進め方

1. 事前確認: `docs/projects/{案件名}/requirements.md` の存在とステータス（「確定」であること）を確認する。
   無い・未確定なら停止してユーザーへ依頼する。
2. 対象案件のジョブが1本か複数本かを想定しつつ、以下を**順番に**実行する（並列化しない。
   `development-guide.md` §2.1 の工程フローに従う）。
3. 各工程は Agent ツールで起動する。サブエージェントへのプロンプトには必ず以下を含める:
   - 対象の `.claude/skills/{skill}/SKILL.md`（および参照する `templates/`・`references/`）を
     読んで指示どおりに実行すること
   - 入力ファイルの絶対パス（前工程の成果物）
   - その工程の検証ループ（該当Skill・development-guide.md §5 に規定されたもの）を
     実際に実行し、成功するまで（上限内で）繰り返すこと
   - 完了時に「成果物パス」「検証結果（コマンドと結果）」「未確定・要確認事項の有無」を
     簡潔に返すこと
4. **基本設計→レビュー**:
   - `basic-design` サブエージェント（Opus）で `basic-design.md` を作成
   - `review-design` サブエージェント（Opus）で `basic-design.md` をレビューし、
     **[Must]/[Should]/[Nit] は全てそのサブエージェント自身が即座に修正まで行う**
     （指摘を返すだけで終わらせない。§「レビュー指摘の扱い」参照）
   - `[Ask]`（設計意図の確認）が残った場合のみ、主エージェントが受け取ってユーザーに確認する
5. **詳細設計→レビュー（ジョブごとに繰り返す）**: 基本設計書のジョブ一覧に載っている各ジョブIDについて、
   `detail-design` → `review-design` を4と同様の手順（Opus、指摘は自己修正）で実行する
6. **実装〜結合テスト（ジョブごとに繰り返す）**: `implementation` → `unit-test` → `integration-test`
   をジョブごとに Sonnet サブエージェントで実行する（各Skillが規定する検証ループを含む）
7. **コードレビュー**: 対象パッケージ（実装したジョブ全体）に対して `review-code` サブエージェント（Opus）
   を実行し、指摘を**全て自己修正**したうえで `./mvnw verify` が通ることまで確認させる
8. **システムテスト**: `system-test` サブエージェント（Sonnet）でシナリオ作成・実施・記録まで行う。
   Docker 未起動などスコープ外の前提NGは、そのサブエージェントの結果を見て主エージェントが
   ユーザーへ依頼する（§「停止して確認するタイミング」）
9. **PR作成**: 主エージェントが直接、GitHub Flow（`development-guide.md` §3）に従いブランチ作成・
   コミット・プッシュ・`gh pr create` を実施する（PRテンプレートに設計書リンクとレビュー実施記録を記載）。
   ここは「確認なしで進めてよい」対象なので、ユーザーに実行可否を尋ねない
10. 最後に、実行した全工程・各工程の検証結果・PRリンクを簡潔にまとめて報告する

## レビュー指摘の扱い（重要）

- `review-design` / `review-code` サブエージェントは、検出した **[Must]・[Should]・[Nit] 相当の指摘を
  必ずその場で修正する**。「反映してよいか」をユーザーに尋ねるステップは挟まない
  （細かい指摘でも全て対応する、という方針のため）
- **[Ask]**（設計意図・業務判断の確認）は性質が異なる。答えを誤ると手戻りになるため、
  サブエージェントは修正せず「確認事項」として持ち帰らせ、主エージェントが
  `AskUserQuestion` でユーザーに確認してから該当箇所を反映する
- 指摘を修正したら、そのサブエージェント自身の中で再度ビルド・テストを実行し、
  デグレがないことを確認してから完了報告させる

## 停止して確認するタイミング

デフォルトは「確認なしで最後まで進める」。ただし以下は**手戻りにつながる**ため、必ず一度止めて
主エージェントが `AskUserQuestion` でユーザーに確認する。

- 要件定義書の「未確定事項」が設計判断に影響する場合（本来はSkill開始前に解消済みのはずだが、
  基本設計・詳細設計サブエージェントが新たな未確定・矛盾を発見した場合を含む）
- 各設計工程で `[Ask]` 区分の指摘が残った場合（上記）
- 検証ループがOpusへ昇格しても解消しない場合（`development-guide.md` §5.3 の早期エスカレーション）
- システムテストの前提条件（Docker起動、外部依存の有無）が満たせない場合
- 破壊的操作が必要になった場合（既存データの削除、Flyway適用済みファイルの変更が必要と判明した等）

上記に該当しない限り、PR作成まで自動で進めてよい。

## 禁止事項

- 工程の順序を入れ替えたり、レビュー工程を省略したりしない
- レビュー指摘の「対応不要」判断をサブエージェント・主エージェントの独断で行わない
  （[Must]/[Should]/[Nit] は修正、[Ask] は必ずユーザーに確認）
- 検証ループを通すために検証自体を弱める（カバレッジ閾値変更・テスト削除等）ことは、
  各工程のSkill定義同様に禁止（`development-guide.md` §5.4）
- PR作成（git push・`gh pr create`）をサブエージェントへ委譲しない
