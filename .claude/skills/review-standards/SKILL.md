# 規約レビュー Skill

実装コードを規約・チェックリストと突き合わせてレビューし、指摘一覧を作成する。

## 入力と出力（工程連鎖）

| | 内容 |
|---|---|
| 入力 | 実装コード＋テストコード（対象パッケージ/差分）と詳細設計書 |
| 基準 | `docs/coding-standards.md`、`docs/architecture.md`、`references/code-review-checklist.md` |
| 出力 | レビュー指摘一覧（会話で提示）。反映後、PR 本文に実施記録を残す（実装 PR 用テンプレート `.github/PULL_REQUEST_TEMPLATE/implementation.md` のレビュー実施記録） |
| 次工程 | 指摘反映 → PR 作成（`docs/development-guide.md` §3） |

## 進め方

1. 詳細設計書を読み、**設計と実装の一致**を最初に確認する（差異があれば Must 指摘）
2. `references/code-review-checklist.md` の全項目を確認する
3. `./mvnw clean verify` の結果（テスト・Checkstyle・SpotBugs・カバレッジ）を確認する
4. 同じ差分に対して、Claude Code 組み込みの `/code-review`（Skill ツールの `code-review`）を必ず実行する。
   手順1〜3はチェックリスト（規約）の確認で、データの境界値（DB の型・桁とファイルのバイト長の食い違いなど）や
   失敗経路（途中失敗からのリスタート、パスの衝突など）の不具合は拾いにくいため、両方を通す
   - `/code-review` の指摘も下表の区分（Must/Should/Ask）に分類し直し、手順1〜3の指摘と1つの一覧にまとめる（出典列に `/code-review` と書く）
   - 設計書・決定事項どおりの実装でも、データの範囲や失敗経路で壊れる指摘は除外しない。直すのに設計の改訂が要るものは [Ask] にする
   - 除外する指摘（事実誤認・対象外）は、一覧の最後に理由を1行で残す
5. 指摘一覧を提示する（形式は下表。修正はユーザー了承後）

| # | 区分 | 出典 | ファイル:行 | 指摘 | 根拠 |
|---|---|---|---|---|---|

- **[Must]** 規約違反・基盤部品の独自実装・バグ・データ破損リスク（修正必須）
- **[Should]** 性能・保守性・テスト不足（原則修正）
- **[Ask]** 実装意図の確認

**例外（パイプライン実行時）**: 呼出元（`sdd-pipeline` Skill）から自己修正を指示された場合は、
[Must]/[Should]（手順4の `/code-review` 由来を含む）を了承取得なしでその場で修正し、修正後に `./mvnw clean verify` が通ることを確認したうえで、
指摘一覧と修正内容を完了報告に含める。[Ask] は修正せず「確認事項」として呼出元へ返す。

## 最重要観点（順に確認する）

1. **基盤部品の利用**: implementation Skill の部品対応表と突き合わせ、独自実装がないか
   （HTTP直呼び・自前CSVパース・自前ログ・RuntimeException直接送出は即 Must）
2. **設計との一致**: Step構成・チェック仕様・エラー処理が詳細設計書どおりか
3. **リスタート安全性**: Reader の状態保存、Processor の副作用なし、冪等な書込
4. **トランザクション**: 洗い替えの単一Tx、チャンクコミットへの介入がないこと
5. **性能**: カーソルフェッチ、ループ内1件ずつのMapper呼出がないこと、N+1
6. **Batch 6 準拠**: 5系API・`batch.item.*` パッケージの混入、`listener((Object)...)` キャスト
7. **テスト**: 観点表準拠、正常/警告/異常/リスタートの結合テスト有無
