# 設計レビュー Skill

設計書を方式設計書（SSoT）・チェックリストと突き合わせてレビューし、指摘一覧を作成する。

## 入力と出力（工程連鎖）

| | 内容 |
|---|---|
| 入力 | `docs/projects/{案件名}/basic-design.md` または `detail-design/{ジョブID}.md` |
| 基準 | `docs/architecture.md`（方式設計書）、`references/design-review-checklist.md` |
| 出力 | レビュー指摘一覧（会話で提示）。指摘反映は設計書を直接更新し、変更履歴に記録する |
| 次工程 | 指摘反映後に `/implementation` へ進む |

## 進め方

1. 対象設計書と、その入力になった前工程の成果物（要件定義書/基本設計書）を読む
2. `references/design-review-checklist.md` の全項目を確認する
3. 指摘は以下の形式・区分で一覧化する

| # | 区分 | 箇所 | 指摘 | 根拠（architecture.md の節など） |
|---|---|---|---|---|

- **[Must]** 方式設計違反・実装不能・整合性エラー（修正必須）
- **[Should]** 品質・運用リスク（原則修正）
- **[Ask]** 設計意図の確認（質問）

4. ユーザーの了承を得て設計書へ反映する（勝手に設計判断を変えない）

**例外（パイプライン実行時）**: 呼出元（`sdd-pipeline` Skill）から自己修正を指示された場合は、
[Must]/[Should] を了承取得なしでその場で設計書へ反映し、指摘一覧と修正内容を完了報告に含める。
[Ask] は修正せず「確認事項」として呼出元へ返す（設計意図の判断は代行しない）。

## レビューの姿勢

- 「方式設計書に準拠しているか」を最優先で確認する（個人の好みは指摘しない）
- 指摘には必ず根拠（architecture.md の節番号・チェックリスト項目・要件定義書の記述）を付ける
- 前工程との**トレーサビリティ**を確認する（要件にない機能が増えていないか、要件の漏れがないか）
