# 設計レビューチェックリスト

## A. トレーサビリティ

- [ ] 要件定義書の全処理が基本設計のジョブ一覧でカバーされている（漏れなし）
- [ ] 要件にない機能が追加されていない（追加する場合は要件定義書を先に改訂）
- [ ] 未確定事項が設計判断に影響していない（影響する場合は確定を先行）

## B. 方式選定（architecture.md §3）

- [ ] Chunk / Tasklet の選定理由が判断基準（§3.1）に沿って記載されている
- [ ] 集計SQLで完結する処理を Chunk にしていない（データをJavaに持ち出していない）
- [ ] 件数無制限の入力を Tasklet で全件処理していない
- [ ] Step 分割が 1 Step 1 責務になっている
- [ ] Step 間のデータ受け渡しが DB/ファイル経由（ExecutionContext は少量メタ情報のみ）

## C. トランザクション・リラン（§4・§6）

- [ ] 洗い替えは truncate + insert が同一トランザクションに収まる設計か
- [ ] リスタート可否（再開 or 最初から）が明記され、根拠があるか
- [ ] 取込の冪等性（UPSERT / 洗い替え）が設計されているか
- [ ] 成功済み再実行の扱い（業務パラメータ変更）が運用として書かれているか
- [ ] リスタートに JDBC ジョブリポジトリが前提であることを踏まえているか（§9.1）

## D. エラー処理（§5）

- [ ] エラー事象ごとに 業務/システム の分類と動作（Skip/即失敗）が表になっている
- [ ] Skip は業務エラーのみ・上限件数が定義されている
- [ ] Skip レコードの退避先と手動リカバリの流れが書かれている
- [ ] 警告終了（終了コード2）の条件が定義されている

## E. IF・テーブル設計（§9）

- [ ] 固定長レイアウトは**バイト数**で定義されている（文字数ではない）
- [ ] 文字コード・改行コードが明記されている
- [ ] テーブルは app スキーマ・snake_case、Flyway のファイル名が採番されている
- [ ] 大量読取がカーソルフェッチ前提になっている（全件 selectList をしていない）

## F. 命名・運用（§7・§8・§11）

- [ ] ジョブ名・Step名・パッケージ名が命名規約どおり
- [ ] ジョブパラメータが定義され、必須/任意が明確
- [ ] 終了コードが規約（0/2/1）から逸脱していない（カスタム ExitStatus を増やしていない）
- [ ] スケジュール・依存フロー・失敗時の運用（通知先・リラン手順）が書かれている
- [ ] 処理時間の見込みとチャンクサイズ初期値に根拠（件数規模）がある

## G. 詳細設計のみ

- [ ] 使用する基盤部品がクラス名まで特定されている（独自実装前提になっていない）
- [ ] 入力チェック仕様が 項目×チェック内容×エラー時の扱い で網羅されている
- [ ] 設計書だけで実装可能な粒度になっている（実装者への口頭補足が前提になっていない）
- [ ] テスト観点メモが記載されている（テスト工程への引き継ぎ）
