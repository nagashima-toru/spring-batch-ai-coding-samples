# T-03 ORDER-001 1.4 版の結合テスト（最初からのリスタート・Issue #74 の再現）を OrderDailySalesJobIT に書く

## 目的

- batch-core のカバレッジ80%を含むビルドが通る：`./mvnw clean verify -DskipITs -pl batch-core 2>&1 | grep -c '^\[INFO\] BUILD SUCCESS$'` の出力が `1`
- 結合テストと batch-sample のカバレッジ80%を含むビルドが通る：`./mvnw clean verify 2>&1 | grep -c '^\[INFO\] BUILD SUCCESS$'` の出力が `1`
- 3行目のビルドの後、`OrderDailySalesJobIT` が失敗・スキップなしで実行されている：`grep -c 'Failures: 0, Errors: 0, Skipped: 0' batch-sample/target/failsafe-reports/com.example.batch.sample.job_order_daily_sales.OrderDailySalesJobIT.txt` の出力が `1`
- 1.4 版の3つのリスタートのテストがあり、旧方式のテストが無い：`OrderDailySalesJobIT.java` に対し `grep -c 'void Step4の途中でDB例外により失敗しても同一パラメータでリスタートすると最初から取り込み直し1回で成功した場合と同じ結果になる'`・`grep -c 'void 実行AをStep4で失敗させ別の対象日の実行Bを完了させてからAをリスタートすると両日の明細と集計がそれぞれの入力どおりになる'`・`grep -c 'void 実行AをStep5で失敗させ別の対象日の実行Bを完了させてからAをリスタートすると対象日の明細が0件にならない'` がそれぞれ `1`、`grep -c '続きから取り込み'` が `0`

## 決定済み
- テストメソッド名は次の3つをそのまま使い、`void <名前>()` の形（`void` とメソッド名の間は半角空白1つ）で書く
  - `Step4の途中でDB例外により失敗しても同一パラメータでリスタートすると最初から取り込み直し1回で成功した場合と同じ結果になる`（既存の `Step4の途中でDB例外により失敗しても同一パラメータでリスタートすると続きから取り込みリスタートをまたいだ重複もSkipされる` を置き換える。旧名のメソッドは残さない）
  - `実行AをStep4で失敗させ別の対象日の実行Bを完了させてからAをリスタートすると両日の明細と集計がそれぞれの入力どおりになる`
  - `実行AをStep5で失敗させ別の対象日の実行Bを完了させてからAをリスタートすると対象日の明細が0件にならない`
- 1つ目（同一実行回のリスタート）：既存のテストと同じく、トリガで Step 4 の2チャンク目を失敗させる。入力にはファイル内の重複行を1行入れ（例：最終行に `R001,5,...` を置く）、リスタート後に次を確かめる：終了コードが `COMPLETED_WITH_WARNING`（重複1件の Skip。1回で成功した場合と同じ）、明細・集計が入力どおり、エラーファイルの行数が1（同じ行が重複しない）、リスタートの実行で Step 4 の読込件数が入力の全データ行数（ファイルの先頭から読み直した）。失敗後・リスタート前にエラーファイルがあれば中身を残したままリスタートし、Step 3 で削除されることも確かめてよい
- 2つ目・3つ目（Issue #74 の再現）：A は targetDate=2026-10-11、B は targetDate=2026-10-12 にする。既存の `parameters(...)` は targetDate を `TARGET_DATE` に固定しているので、targetDate を受け取るオーバーロードを足す。B の受注番号は A と重ならない値にする（`app.order_detail` の主キーは受注日を含まない `(order_no, line_no)` のため。例：A は `A001`…、B は `B001`…）。A と B の入力ファイル・エラーファイルは別のパスにする
  - 2つ目：A を Step 4 の2チャンク目でトリガにより失敗させ（A の行だけを失敗させる条件にする）、トリガを外して B を完了させ、A をリスタートする。A が COMPLETED、10/11 の明細・集計が A の入力どおり、10/12 の明細・集計が B の入力どおり（B の完了直後と同じ）であることを確かめる
  - 3つ目：A を Step 5 で失敗させる（`app.order_detail` への INSERT で例外を起こすトリガを一時的に足す。既存のテストと同じく `finally` で必ず外す）。トリガを外して B を完了させ、A をリスタートする。10/11 の明細が A の入力どおり（0件でない）、10/12 の明細・集計が B のままであることを確かめる
- トリガ・関数は既存のテストと同じく `app.` に作り、テストの中で `finally` で消す（他のテストに影響させない）。トリガの名前は既存の `it_fail_trigger` と同じでもよい
- 既存のほかのテストは変えない（1.4 版で期待が変わるのはリスタートのテストだけ）。クラスの Javadoc の観点の説明に古い記述があれば直してよい
- 結合テストには Docker が要る。`docker info` が失敗する時は `docs/development-guide.md` §1.4 の手順で用意する。ビルドには JDK 25 が要る（同じ節）
- 実装（`src/main`）の不具合を見つけた時は、直さずに blocked にして question に書く（このタスクの成果物は結合テストだけ）
