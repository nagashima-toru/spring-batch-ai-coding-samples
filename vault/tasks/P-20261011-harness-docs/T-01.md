## 決定済み
- 新しい節の見出しは `### 2.4 ハーネスで実装以降を進める場合` とする（一字一句この文字列。T-02 が `CLAUDE.md` からアンカー `#24-ハーネスで実装以降を進める場合` でリンクするため、見出しに記号を足さない）。置き場所は §2.3 の節の末尾（`## 3. ブランチ運用・PR` の直前）
- §2.4 に書く内容（この順）：(1) ハーネスで進めるのは詳細設計がレビュー済み（`/review-design` を通った）ジョブの implementation〜system-test で、要件定義〜設計レビューは従来どおり人と Skills で対話して進める、(2) `/plan` に渡すゴール文の例、(3) 使い分け表、(4) 1計画1ジョブで5工程のタスクに分けることと、ルールは `vault/rules/` にあること（パスで参照するだけで、ルールの本文は書き写さない）
- ゴール文の例は fenced code block（```text）の中に次の1行をそのまま書く：`> /plan docs/projects/sales/detail-design/SALES-001.md（レビュー済み）の SALES-001 を implementation〜system-test のタスクに分けて実装・検証する`
- 使い分け表のヘッダ行は `| 観点 | /sdd-pipeline | ハーネス（/plan・/run） |`（一字一句この文字列）。行見出しは `対象工程`・`開始の前提`・`判断が要る時`・`検証のしかた` の4行で、この4語をそれぞれ行頭の `| ` の直後に書く。行を足してもよいが、この4語を他の行の行見出しに使わない
  - 対象工程：sdd-pipeline は basic-design〜system-test と PR 作成、ハーネスは implementation〜system-test（要件定義〜設計レビューは人と Skills で対話）
  - 開始の前提：sdd-pipeline は確定済みの requirements.md、ハーネスはレビュー済みの詳細設計書
  - 判断が要る時：sdd-pipeline は主エージェントへの報告とモデル昇格（§5.3）、ハーネスは creator が `[Ask]` などを blocked にし、人が `/plan unblock` で答える
  - 検証のしかた：sdd-pipeline は各工程内の検証ループ（§5）、ハーネスは creator と別の verifier が受け入れ基準（`./mvnw verify -DskipITs`、結合テストを含むタスクは `./mvnw verify`）で判定する
- `sdd-pipeline` は廃止せず併存させる（既存の利用者と手順を壊さないため）と §2.4 に1文書く
- §5.3 への追記は、既存の「モデル昇格」段落の後（`### 5.4` の前）に、行頭を `**ハーネスで実行する場合**:` とする1段落を足す。この段落は改行せず1行で書き、「モデル昇格」「attempt」「blocked」の語をこの順に含める。内容は「ハーネス（`/plan`・`/run`）ではモデル昇格（Sonnet→Opus）を使わない。verifier が FAIL にしたタスクは attempt を上げて再試行し、上限（`HARNESS_MAX_ATTEMPTS`、既定3）を超えたら blocked にして人に引き継ぐ」
