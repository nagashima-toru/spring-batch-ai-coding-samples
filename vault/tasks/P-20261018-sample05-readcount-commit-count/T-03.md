## 決定済み
- `Sample05JobConfig`
  - 定数 `public static final String USER_READ_COUNTER_NAME = "sample05UserReadCounter";` を足す（Javadoc：取得件数を数える `CountingItemStreamReader` の名前。Step の ExecutionContext のキー `sample05UserReadCounter.item.count` に使われる）
  - `sample05UserReader` Bean（`@StepScope`、戻り値の型 `ItemStreamReader<ApiUserResponse>` は変えない）は、今の2つの分岐で作る Reader をローカル変数 `delegate` に入れ、最後に1回だけ `return new CountingItemStreamReader<>(USER_READ_COUNTER_NAME, delegate);` で包んで返す（`new CountingItemStreamReader` を書くのはこの1か所だけ）
  - Listener の登録は `.listener(new ApiUserReadCountListener(USER_READ_COUNTER_NAME))` にする（`(Object)` キャストはしない。CLAUDE.md のハマりどころ3）
  - `USER_READER_NAME`・`USER_JSON_READER_NAME` は委譲先の Reader の名前（読込位置の保存とリスタートに使う）として残す。Javadoc から「件数に使う」旨があれば消す。`read.count` への言及は事実なので JobConfig では残してよい
  - クラス Javadoc の Step 構成の説明は変えなくてよい（取得件数の数え方を書いていないため）
- `ApiUserReadCountListener`
  - コンストラクタは `public ApiUserReadCountListener(String counterName)` の1引数に変える（複数の Reader 名を探す仕組みは要らなくなる）
  - `afterStep` は Step の ExecutionContext から `CountingItemStreamReader.countKey(counterName)` の値を読み、Step の状態に関係なくその値（無ければ0）を Job の ExecutionContext の `READ_COUNT_KEY`（`apiUserReadCount`、名前は変えない）に `putLong` で上書きする。COMPLETED の時に1を引く処理は消す
  - 値が無く、Step が COMPLETED の時だけ警告ログ（`取込Stepの取得件数が見つかりません。取得件数を0件とします: counterName={}` の趣旨）を出す。値は `((Number) value).longValue()` で読む
  - 定数 `READER_READ_COUNT` と `ExecutionContextUserSupport` の直接利用は消す。ファイル内に `read.count` の文字列を残さない
  - クラス Javadoc を書き直す：取得件数は `CountingItemStreamReader` が保存したコミット済みの件数（Reader が返した null 以外の件数＝書込件数＋Skip 件数）で、終端の null を数えないため Step が STOPPED・FAILED で終わっても件数がずれないこと（Issue #81）、readCount を使わない理由（Issue #79）、リスタートで上書きする理由、Job の ExecutionContext に置く理由。「1を引く」「1件を引く」という語は使わない
- `ApiUserReadCountListenerTest`
  - キーは `CountingItemStreamReader.countKey(Sample05JobConfig.USER_READ_COUNTER_NAME)` で組み立てる（`.read.count` を使う既存の定数は消す）
  - 次の2つはこの名前のまま書く：`void 取込Stepが最後のチャンクのコミット後に停止した場合_コミット済みの件数をそのまま保存する()`（STOPPED、キーに5 → 5を保存）・`void 取込Stepが最後のチャンクのコミット後に失敗した場合_コミット済みの件数をそのまま保存する()`（FAILED、キーに5 → 5を保存）
  - このほか、COMPLETED でキーの値をそのまま保存する（readCount に別の値を入れても使わない）、キーが無い時に0件を保存する（COMPLETED と FAILED の両方）、リスタートで前回の Job の値に足し込まず上書きする、の各テストを残す・書き直す。既存のテスト名のうち「終端の読込1件を引いた」「終端の読込を引かずに」を含むものは、数え方が変わったので名前ごと書き直す
- `Sample05ApiImportJobIT` はこのタスクでは変えない（T-04）。ただし既存の結合テストの期待値（取得件数5・6・2など）は数え方を変えても同じ値になる想定。`./mvnw clean verify`（結合テスト）はこのタスクの基準に入れない
- 受け入れ基準4の範囲は `batch-sample` と `docs` の `*.java`・`*.md`。`vault/`（計画一式。Issue の経緯として語を含む）と `target/`（ビルド生成物。`--include` で除く）は対象外
