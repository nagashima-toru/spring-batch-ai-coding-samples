## 決定済み
- 改訂するのは「処理の流れ」節の `sample05.01ImportStep` の下の箇条（現状 24〜30 行目）。ほかの節（デモする機能・リトライ方針など）は、下の「デモする機能」への1行追加を除き変えない
- 新しい数え方として、次の内容を書く（言い回しは整えてよいが、「この語を書く」とした文言はそのまま書く）
  - 取得件数は、取込 Step の Reader が返した null 以外の件のうち、コミット済みのチャンクに含まれる件数（＝書込件数＋入力チェック・書込で Skip した件数）とする
  - batch-core の `CountingItemStreamReader` が Reader（`RestApiPagingItemReader`、`inputFile` 指定時は `JsonItemReaderFactory` の Reader）を包んで数え、チャンクのコミットごとに Step の ExecutionContext の `sample05UserReadCounter.item.count` に保存する（この2つの語をバッククォート付きで書く）。リスタート時はこの値を引き継いで続きから数えるため、前回の件数に足し込まない
  - Step の終了時（状態を問わない）に、この件数を Job の ExecutionContext の `apiUserReadCount` に保存する（前回の値は上書きする）。値が無い時は0件とし、COMPLETED なのに無い時（設定の誤り）は警告ログを出す
  - 終端を確かめる null の読込は数えないため、「最後のチャンクのコミット後に停止・失敗しても取得件数は変わらない」（この文言をそのまま1回だけ書く）。Issue #81 の経緯（以前は COMPLETED の時だけ終端の読込1件を引いており、最後のチャンクのコミット後に STOPPED・FAILED で終わると1件多くなった）を1文で添える。その文では「1を引く」という語を使わない（例：「終端の読込を差し引く推定をやめた」）
  - 読込時の例外は Skip しない（`BusinessSkipPolicy` が Skip するのは `BusinessException`・`FlatFileParseException` だけで、Reader の例外は `SystemException` などになる）ため、Reader が返さなかった件は数え方に影響しない
  - StepExecution の readCount を使わない理由（Issue #79）の箇条は残す
- 削除するもの：Reader の読込位置（`sample05UserReader.read.count`・`sample05UserJsonReader.read.count`）から求める記述と、「COMPLETED の時は1を引く」の記述。解説の中に `read.count` の文字列を残さない
- 「デモする機能」節に `CountingItemStreamReader` の1行（コミット済みの取得件数を数えて保存し、件数の突き合わせに使う）を足す。解説中で `CountingItemStreamReader` は何回書いてもよい
- `batch-sample/docs/README.md` の「基盤部品別の実例ジョブ索引」の表に、`RestApiPagingItemReader` の行の直後へ `` | `CountingItemStreamReader` | `job05_api_import` / `Sample05JobConfig`（件数 API と突き合わせる取得件数） | `` の1行を足す。ほかの行は変えない
- `.claude/skills/implementation/SKILL.md` の「最重要ルール」表に、「API のページング取得」の行の直後へ `` | Reader が返した件数（コミット済み）の保存 | `CountingItemStreamReader`（Reader を包む） | `` の1行を足す。ほかの行・節は変えない
- `docs/architecture.md` は変えない（基盤部品の一覧を持たないため。計画票の分割方針に記載）。`docs/coding-standards.md` §4.2 は部品の分類だけを挙げているので変えない
- 部品の名前・保存キーは T-02・T-03 と共通で、`com.example.batch.core.item.CountingItemStreamReader`、キーは `<名前>.item.count`、sample05 での名前は `sample05UserReadCounter`。解説ではパッケージを書かなくてよい
