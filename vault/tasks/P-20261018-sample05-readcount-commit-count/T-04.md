## 決定済み
- テストメソッド名は `void 最後のチャンクのコミット後に停止した場合_リスタートで取得件数がコミット済みの件数のまま件数の突き合わせが通る() throws Exception` とする
- 再現の組み立て（既存のスタブ設定のまま：ユーザー5件、ページサイズ2、チャンクサイズ3）
  - チャンク1は U001〜U003、チャンク2は U004・U005 と終端の null（page=2 が1件でページサイズ未満のため、`RestApiPagingItemReader` は次のページを取らずに null を返す）。チャンク2のコミットで委譲先 Reader の読込位置は6（終端の null の読込を含む）になる。これが Issue #81 の条件
  - スタブに `static volatile boolean` のフラグ（例：`stopOnLastPage`。`@BeforeEach` で false に戻す）を足し、`/users` の page=2 の要求でフラグが真なら、フラグを false にしてから実行中のジョブ（`JobRepository#findRunningJobExecutions(Sample05JobConfig.JOB_NAME)` で取る）を `JobOperator` で停止要求し、その後に page=2 の応答を返す。フラグを1回で下ろすのは、リスタートで page=2 を取り直した時に再び停止しないため
  - 停止要求はチャンク2の読込中に出るので、Spring Batch はチャンク2をコミットした後で停止を検知し、取込 Step を STOPPED で終える想定。1回目の実行の assert は受け入れ基準2のとおり（ジョブ・取込 Step が STOPPED、writeCount 5、`Sample05JobConfig.USER_READER_NAME + ".read.count"` のキーの値が6、`apiUserReadCount` が5）。読込位置6の assert は再現条件を満たしたことの証拠として必ず書く（修正前の実装なら `apiUserReadCount` は6になり、このテストは落ちる）
  - リスタートは既存のテストと同じく `jobOperator.restart(<1回目の JobExecution>)`。assert は受け入れ基準2のとおりで、加えて `app.api_user` の件数が5であることも確かめる
  - 停止を検知するタイミングが想定と違い（例：チャンク2のコミット前に検知されて writeCount が3になる）、再現条件を満たせない時は、IT の中だけで停止要求を出す場所（page=2 の応答の前か後か、など）を変えて合わせてよい。本番コード（`src/main`）とほかのテストは変えない。それでも STOPPED かつ読込位置6の状態を作れない時は、観測した状態（ジョブ・Step の状態、writeCount、読込位置）を question に書いて blocked にする
- `JobOperator` の停止の API は Spring Batch 6 のシグネチャを確認して使う（5系のサンプルを流用しない。CLAUDE.md の禁止事項）。`JobRepository` は `@Autowired` で取ってよい。スタブのハンドラ（static）から使うため、`@BeforeEach` で static フィールドに入れる形でよい
- 既存の6件ちょうどのテストのコメント（「終端の null だけを読む空のチャンクでも読込位置が保存される」）は、数え方が変わったので「終端の null だけを読む空のチャンクでも取得件数が保存される」趣旨に直してよい。既存テストの期待値は変えない（変えないと通らない時は数え方の実装の誤りなので、T-03 の成果物は直さず blocked にする）
- maxItemCount の経路の結合テストは作らない（sample05 は maxItemCount を使わない。計画票の分割方針）
- `./mvnw clean verify` には Docker（Testcontainers の PostgreSQL 16）と JDK 25 が要る（`docs/development-guide.md` §1.4）
