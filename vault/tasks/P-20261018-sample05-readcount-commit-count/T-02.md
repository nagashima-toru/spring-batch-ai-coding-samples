# T-02 batch-core に件数を数えて保存する Reader デコレータ CountingItemStreamReader を足す

## 目的
Reader が返した null 以外の件数を数え、チャンクのコミットごとに Step の ExecutionContext へ保存し、リスタートで引き継ぐ基盤部品を batch-core に足す。終端の null の読込を数えないので、Step の終了状態に左右されないコミット済みの件数が得られる（Issue #81 の対応案）。

## 決定済み
- 形は Reader デコレータ（`ItemStreamReader` の実装で、別の `ItemStreamReader` を包む）にする。理由：
  - 件数の保存を `ItemStream.update` で行うと、Reader の読込位置（`<Reader名>.read.count`）と同じく、チャンクのトランザクションの中で Step の ExecutionContext に書かれてコミットと一緒に確定し、ロールバックしたチャンクの分は残らない。リスタート時は `open` で引き継げる。既存の `read.count` と同じ仕組みに乗るので、コミット済みの件数と一致する
  - ChunkListener は Spring Batch 6 の新チャンクモデルで API が変わっており、読んだ件の数を直接は受け取れない。StepExecution の件数（readCount・writeCount・skip 系）は1回の実行ごとにリセットされ、readCount はロールバックしたチャンクの分も含むことがある（Issue #79）ので使わない
  - 既存の batch-core の構成（config exception execution http item listener tasklet）のうち、Reader 部品を置く `item` パッケージに置く。新しいパッケージは作らない
- クラス：`com.example.batch.core.item.CountingItemStreamReader<T>`。宣言は `public class CountingItemStreamReader<T> implements ItemStreamReader<T>`（`org.springframework.batch.infrastructure.item.ItemStreamReader`）
- コンストラクタ：`public CountingItemStreamReader(String name, ItemStreamReader<T> delegate)`。`name` が null・空白だけ、または `delegate` が null なら `IllegalArgumentException`（`RestApiPagingItemReader` の引数検査と同じ流儀。メッセージは日本語）
- 保存キー：`public static String countKey(String name)` が `new ExecutionContextUserSupport(name).getKey("item.count")`（＝`<名前>.item.count`）を返す。キーの後ろの部分は定数 `public static final String COUNT_KEY_SUFFIX = "item.count"` にする。名前は委譲先の Reader 名と別の名前にする（Javadoc に書く）
- `read()`：委譲先の `read()` の結果が null でなければ件数を1増やして返す。null（終端）は数えない。委譲先の例外はそのまま投げる（数えない）
- `open(ExecutionContext)`：委譲先の `open` を呼んだ後、キーがあればその値（`((Number) value).longValue()` で読む。Long 以外で復元されても読めるように）を件数にし、無ければ0にする
- `update(ExecutionContext)`：委譲先の `update` を呼んだ後、`putLong(countKey(name), 件数)` で保存する
- `close()`：委譲先の `close` を呼ぶ。件数は消さない
- 件数を返す `public long getCount()` を持つ（テストと調査用）
- スレッドセーフにしない（マルチスレッド Step では使わない旨を Javadoc に書く）。委譲先が読込位置を保存しない（`saveState=false` でリスタート時に先頭から読み直す）場合は、引き継いだ件数に同じ件を足し直してしまうため使わない旨も Javadoc に書く
- Javadoc には用途（件数の突き合わせに使うコミット済みの件数＝書込件数＋Skip 件数）、終端の null を数えないので Step の終了状態（COMPLETED・STOPPED・FAILED）に左右されないこと、`@StepScope` の Reader Bean の戻り値で包む使い方の例を書く（`RestApiPagingItemReader` の Javadoc の書き方にそろえる）
- 単体テストは Spring コンテキストを使わず（方式設計 §12）、委譲先は Mockito のモックかテスト内の小さな `ItemStreamReader` 実装にする。テストメソッド名は日本語（条件＿期待結果の形にこだわらず、次の4つはこの名前のまま書く）
  - `void nullでない件だけを数え終端のnullは数えない()`：委譲先が a, b, null を返す時、件数が2で、`update` 後のキーの値も2
  - `void updateで件数を名前とitem.countをつないだキーに保存し委譲先のupdateも呼ぶ()`：キーが `<名前>.item.count` で、委譲先の `update` に同じ ExecutionContext が渡る
  - `void openで保存済みの件数を引き継ぎ続きから数える()`：キーに3を入れた ExecutionContext で `open` し、1件読むと件数が4。委譲先の `open` も呼ばれる
  - `void closeを委譲先に伝える()`
  - このほか、キーが無い時に0から数えること・引数検査の例外を確かめるテストを足し、batch-core のカバレッジ80%を満たす
- maxItemCount・スキャンモード（書込 Skip 後の1件ずつの再処理）は Reader を読み直さないので、この部品の数え方はそれらに依存しない。専用の結合テストは作らない（計画票の分割方針）
- `BatchCoreAutoConfiguration` には登録しない（Bean ではなく、ジョブ側で `new` して使う部品のため）
- sample05 への適用は T-03 で行う。このタスクでは batch-sample を変えない
