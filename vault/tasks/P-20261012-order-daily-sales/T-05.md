- No.1〜6 の各シナリオ詳細に、テンプレートの「目的」「事前条件」「手順」（期待結果と実施結果の列を持つ表）「確認ポイント」「実施結果」「証跡」がそろい、証跡に実際に実行したコマンドの終了コードと、ログ抜粋または件数クエリの結果がある。`grep -c '^- \*\*証跡\*\*' docs/projects/order-daily-sales/system-test/scenarios.md` が `6`（中身は読んで確認）

## 決定済み
- シナリオは次の6つにし、この番号・分類で書く（名前は内容が分かれば言い換えてよい）
  - No.1 業務：日次実行の正常系（EventBridge 想定。`scheduledTime` に UTC を渡し `targetDate`・`inputFile`・`errorFile` を省略して、前日分が既定パスから取り込まれ、明細・集計が入力と突合して一致し、終了コード0。詳細設計書 §7「システムテスト」の2点目）
  - No.2 運用：警告終了の運用（不正行を含むファイル → 終了コード2 → エラーファイルを確認 → 訂正ファイルで新しい `scheduledTime`・同じ `targetDate` により再実行 → 洗い替えで訂正後の内容になり、エラーファイルが別名になる。詳細設計書 §5「成功後の再処理」）
  - No.3 運用：異常終了 → リラン（Step 4 の途中で失敗させ、原因を除いて同一パラメータで再実行し、続きから完走して1回で成功した場合と同じ結果になる。詳細設計書 §5）
  - No.4 運用：二重起動の防止（終了コード1）
  - No.5 運用：入力不備での異常終了（ファイルなし・ヘッダ不正で終了コード1、本テーブル不変）
  - No.6 運用：処理時間（10万件。詳細設計書 §7「システムテスト」の1点目）
- 実施環境はローカル：`docker compose -f docker/compose.yaml up -d` の PostgreSQL 16 と、`./mvnw -DskipTests package` などで作った `batch-sample/target/batch-sample-*.jar` を `--spring.profiles.active=local` で直接起動する（`CLAUDE.md` の実行例）。終了コードはプロセスの終了コードで確かめる
- 実行時のファイル（入力 CSV・エラーファイル・生成した10万件のデータ）はリポジトリの外の `/tmp/claude/P-20261012-order-daily-sales-T-05/` に置く（開始時に `mkdir -p` で作る。既存の中身を前提にしない）。既定パスからの取込（No.1）は `--sample.order-daily-sales.input-dir=/tmp/claude/P-20261012-order-daily-sales-T-05/in` と `--sample.order-daily-sales.error-dir=...` で既定ディレクトリをそこに向けて確かめる。`batch-sample/data/` やリポジトリ内に実行時のファイルを残さない（未コミットのファイルは review への遷移で収集され、宣言外の変更として差し戻されるため）。一時ファイルは消さなくてよい
- テストデータ生成スクリプトは `docs/projects/order-daily-sales/system-test/data/` に置く（形式は任意。シェル・SQL など、ローカルで再現できるもの）。生成した10万件の CSV そのものはコミットしない。個人情報は使わない（要件定義書：個人情報を含まない）
- No.3 の失敗の起こし方は、DB にトリガや制約を一時的に足して後半の行の INSERT を失敗させ、外してから再実行する方法でよい。足した SQL も `data/` に置く
- No.6 の判定：要件の制約（10万件で3時間以内）に収まれば OK。基本設計書の見込み（全体で十数分以内・Step 5 は数十秒以内）を超えた時は OK のまま「確認ポイント」に所見として実測値と見込みとの差を書く。所要時間は `batch.batch_step_execution` の開始・終了時刻かジョブのログから取る
- シナリオ一覧の表は `| No | 分類 | シナリオ名 | 優先度 | 結果 |` の列で、結果の列は `OK` とだけ書く（受け入れ基準の grep が行末の `| OK |` を見る）。各シナリオ詳細の証跡は `- **証跡**:` で始める（テンプレートの書式）
- 不具合（期待結果と違う動作）を見つけたら、コードも設計書も直さずに blocked にし、質問文にシナリオ番号・期待結果・実際の結果を書く（system-test Skill の「修正は implementation 以降の工程を再度通す」）。外部依存などでローカル実施できないシナリオがある時も blocked にする（`vault/rules/creator/skill-workflow.md`）
- シナリオ一覧は `/system-test` の「進め方」1 ではユーザーと合意するが、ここでは上の6つで合意済みとして扱い、「進捗」にシナリオ一覧を書く（`vault/rules/creator/skill-workflow.md` の読み替え）
