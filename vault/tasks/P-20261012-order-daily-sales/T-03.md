## 決定済み
- `AbstractJobIT` を継承する。ただし `uniqueParameters()`（`testRunId` を足す）は使わない。T-01 の Validator が `requiredAndOptional` で未知のキーを拒否するため。JobInstance の重複は `scheduledTime` をテストごとに変えて避ける（例：テストごとに異なる `OffsetDateTime` の文字列を渡す）
- `targetDate` を渡す時は `addLocalDate("targetDate", ...)`、`scheduledTime`・`inputFile`・`errorFile` は `addString`
- 入力 CSV・エラーファイルは `@TempDir` の中に作る。`src/test/resources` にフィクスチャを置かない（成果物は IT の1ファイル）
- 終了状態の検証は既存 IT と同じく `execution.getExitStatus().getExitCode()` で行い、警告は `BatchExitCodes.COMPLETED_WITH_WARNING.getExitCode()`、正常は `"COMPLETED"`、異常は `"FAILED"` と比べる。パラメータ不正（scheduledTime なし）は `jobOperator.start` が `JobParametersInvalidException` を投げることを確認する（`PointExpiryJobIT` の書き方）
- テーブルの初期化は `truncateAppTable("order_detail_work")`・`("order_detail")`・`("daily_store_sales")` を各テストの前に行う
- リスタートの観点は、Step 4 の途中で DB 例外を起こして失敗させ、原因を除いてから `jobOperator.restart(failed)` で再開する。例外の起こし方は、テストから DB にトリガや制約を一時的に足して後半の行で INSERT を失敗させ、再開前に外す方法でよい（`src/main` は変えない）。リスタートをまたいだ重複が Skip されることと、最終結果が1回で成功した場合と同じことを確かめる
- 二重起動防止は、同じジョブの `STARTED` の実行がある状態を作ってから起動して異常終了（`SystemException`）になることを確かめる（`PointExpiryJobIT` などの既存の書き方を参照）
- Step 5 の一意制約違反は、別の日付で同じ `order_no`＋`line_no` を `app.order_detail` に事前登録して起こす
- 「進捗」に観点表を書く：§7「結合テスト」の観点1つにつき1行で「観点 → メソッド名」を対応付ける
- `src/main` は変えない。テストで実装の不具合が見つかったら直さずに blocked にし、質問文にテスト名・期待値・実際の値を書く
- `docker info` が失敗する（Docker が使えない）時は blocked にする（`vault/rules/creator/skill-workflow.md`）
- コミットメッセージは日本語

- （/plan unblock の回答 2026-10-12）T-01・T-02 は -DskipITs で全モジュールの Checkstyle・SpotBugs・単体テストと batch-core のカバレッジ通過までを基準とし、batch-sample のカバレッジは判定しない。batch-sample のカバレッジ80%は T-03 以降の ./mvnw verify で判定する
- （/plan unblock の回答 2026-10-12）(a) T-03 で batch-core/src/main/java/com/example/batch/core/item/ValidatingItemProcessorBase.java の process から final を外し（Javadoc に @StepScope でも使えるよう final にしない旨を書く）、docs/projects/order-daily-sales/detail-design/ORDER-001.md §1 の注記を「継承元の public メソッドも final にしない」に直して変更履歴に記録してよい

- 観点表（§7 結合テスト の観点 → メソッド名）
  - 正常 → 複数店舗複数受注のファイルを取り込むと明細と集計が登録され終了コードCOMPLETEDでエラーファイルは作られない
  - 警告 → 不正行を含むファイルでは正常行だけ取り込みエラーファイルに退避して終了コードCOMPLETED_WITH_WARNINGになる
  - 洗い替え → 同じtargetDateを別のscheduledTimeで2回実行すると1回目の内容が2回目に置き換わり他の日のデータは変わらない
  - ファイルなし → 入力ファイルが存在しない場合は終了コードFAILEDで本テーブルは変わらない
  - ヘッダ不正 → ヘッダ行が不正な場合は終了コードFAILEDで本テーブルは変わらない
  - skipLimit 超過 → Skip件数がskipLimitを超過した場合は終了コードFAILEDで本テーブルは変わらず旧データが残る
  - Step 5 一意制約違反 → 別の日に同じ受注番号と明細番号が登録済みでStep5が一意制約違反になると終了コードFAILEDで本テーブルは全体ロールバックされる
  - リスタート → Step4の途中でDB例外により失敗しても同一パラメータでリスタートすると続きから取り込みリスタートをまたいだ重複もSkipされる
  - 二重起動防止 → 同じジョブの実行中の実行がある状態で起動すると二重起動防止により終了コードFAILEDになり本テーブルは変わらない
  - パラメータ不正 → scheduledTimeを渡さない場合はジョブパラメータ検証エラーで起動失敗し本テーブルは変わらない（InvalidJobParametersException）
- 確認: ./mvnw verify exit 0 BUILD SUCCESS（IT tests=10 errors/skipped/failures=0）、./mvnw verify -DskipITs exit 0 BUILD SUCCESS、@Disabled なし
- 補足: 警告テストのエラーファイルは読取Skip(即時)と加工Skip(チャンク末)で出力順が入れ替わるため、順序でなく内容で検証
