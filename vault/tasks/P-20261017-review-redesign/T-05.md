# T-05 planner ルールにコードを変えるタスクの /code-review の行を書く

## 目的
コードを変えるタスクの受け入れ基準に、`/code-review` で差分の致命的な指摘を確かめる行（verifier ルールを参照する形）を planner が必ず入れるように、planner ルールを書く。

## 入力
- `docs/vault-spec.md` 11節「コードレビューを参照する受け入れ基準」の (1)（行の書き方の既定。読むだけ）
- `vault/rules/verifier/code-review.md`（T-03 で作ったもの。参照先）
- `vault/rules/planner/job-task-split.md`（T-01 の後。工程タスクの分け方。読むだけ）
- `vault/templates/rule.md`（見出し：目的 / ルール / 確認方法）

## 成果物
- `vault/rules/planner/code-review-criterion.md`（新規の1ファイル）

## 受け入れ基準
- ルールの雛形の3見出しがそろっている：`grep -cx -e '## 目的' -e '## ルール' -e '## 確認方法' vault/rules/planner/code-review-criterion.md` の出力が `3`
- コードを変えるタスクの定義が書かれている：`grep -c 'コードを変えるタスク」とする' vault/rules/planner/code-review-criterion.md` の出力が `1`
- 受け入れ基準に入れる行の文言が verifier ルールを参照する形で書かれている：`grep -c '/code-review. で差分に致命的な指摘が残っていない（.vault/rules/verifier/code-review.md. に従って判定する）' vault/rules/planner/code-review-criterion.md` の出力が `1`
- その行に確認コマンドを付けないと書かれている：`grep -c '確認コマンドを併記しない' vault/rules/planner/code-review-criterion.md` の出力が `1`
- 行数の上限との関係が書かれている：`grep -c 'この行は削らない' vault/rules/planner/code-review-criterion.md` の出力が `1`
- 工程タスクとの対応が書かれている：`grep -c 'review-standards の各タスクが通常これに当たる' vault/rules/planner/code-review-criterion.md` の出力が `1`

## 決定済み
- ファイル名は `vault/rules/planner/code-review-criterion.md`（`job-task-split.md` への追記ではなく新しいファイルにする。話題が工程の分け方と別のため）。見出しは `# planner ルール：コードを変えるタスクに /code-review の行を入れる` の後に `## 目的`・`## ルール`・`## 確認方法` の3つ
- 「## ルール」には次の箇条を、文言をこのとおりに書く（各項目は別の行）
  - 「「成果物」が `docs/` 配下のパスと `.md` のファイルだけのタスクは対象外とし、それ以外のパス（Java・SQL・XML・YAML・properties・CSV などのファイルや、`docs/` 以外のディレクトリの宣言）を1つでも持つタスクを「コードを変えるタスク」とする」
  - 「コードを変えるタスクの受け入れ基準には、次の1行を必ず入れる：「`/code-review` で差分に致命的な指摘が残っていない（`vault/rules/verifier/code-review.md` に従って判定する）」」
  - 「この行には確認コマンドを併記しない（verifier が Skill ツールで組み込みの `/code-review` を呼んで判定するため）。`effort`・`--max-findings` などの引数も付けない」
  - 「この行を入れると受け入れ基準が7行を超える時は、ほかの行をまとめて7行以内に収め、この行は削らない」
  - 「ジョブ1本の工程タスク（`vault/rules/planner/job-task-split.md`）では、implementation・unit-test・integration-test・review-standards の各タスクが通常これに当たる。system-test のタスクは成果物で決める」
  - 「差分の外（既存コード）への指摘を直すタスクは起こさない（verifier が対象外として reasons に残し、PR 作成時の取り出しで扱う）」
- 「## 目的」は1〜2行で、「コードを変えるタスクで、規約の確認だけでは拾えない不具合（PR #70 の例）が残ったまま done にならないようにする」旨を書く
- 「## 確認方法」には「コードを変えるタスクの受け入れ基準に上の1行がある。docs だけのタスクには無い」を書く
- 受け入れ基準の行の文言は `docs/vault-spec.md` 11節 (1) の既定「`/code-review` で差分に致命的な指摘が残っていない」に、verifier ルールの参照を後ろに足したもの。verifier ルールは受け入れ基準が参照した時だけ効くため、参照を付ける
- 上の文言の「コードを変えるタスク」とする」「確認コマンドを併記しない」「この行は削らない」などの句は、ファイルの中でそれぞれ1回だけ使う
- `vault/rules/planner/job-task-split.md` は変えない
- 100行以内にする
