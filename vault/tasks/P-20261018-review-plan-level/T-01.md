# T-01 planner ルール code-review-criterion.md を計画単位のレビュータスクへの導入先の補足にする

## 目的
ハーネス（ai-harness#218）の「通常のタスクには `/code-review` の行を入れない。コードを変更する計画の最後に計画単位のレビュータスクを1件足す」と正反対になっている planner ルールを、ハーネスと食い違わない導入先固有の補足だけに縮める。

## 入力
- `vault/rules/planner/code-review-criterion.md`（現行。全面的に書き直す）
- `.claude/agents/planner.md` の「計画単位のレビュータスク」節（ハーネスの正本。写さない）
- `.claude/agents/verifier.md` の「コードレビューを参照する基準の判定」節
- `vault/rules/verifier/code-review.md`（7行目：受け入れ基準の行がこのファイルを参照している時だけ判定に使う）
- `vault/templates/rule.md`（見出し構成：目的 / ルール / 確認方法）

## 成果物
- `vault/rules/planner/code-review-criterion.md`（1ファイル。全面書き直し）

## 受け入れ基準
- 計画単位のレビュータスクの1行目の文言が1回だけ書かれている：`grep -c '/code-review. で計画の差分に致命的な指摘が残っていない（.vault/rules/verifier/code-review.md. に従って判定する）' vault/rules/planner/code-review-criterion.md` の出力が `1`
- ハーネスの節への参照がある：`grep -c '「計画単位のレビュータスク」節に従い、ここには写さない' vault/rules/planner/code-review-criterion.md` の出力が `1`
- 独自のコード変更の判定（`docs/` と `.md`）と旧語が残っていない：`grep -c -e 'コードを変えるタスク' -e '配下のパスと' -e 'タスクの差分' vault/rules/planner/code-review-criterion.md` の出力が `0`
- ハーネスの節（判定・範囲）を写していない：`grep -c -e 'HARNESS_BASE_BRANCH' -e 'merge-base' -e 'でなく、拡張子が' vault/rules/planner/code-review-criterion.md` の出力が `0`
- 見出しが3つそろっている：`grep -c -x -e '## 目的' -e '## ルール' -e '## 確認方法' vault/rules/planner/code-review-criterion.md` の出力が `3`
- planner のルールとして列挙され続ける：`bash scripts/rules.sh planner | grep -c 'code-review-criterion.md'` の出力が `1`

## 決定済み
- ファイルは削除せず、全面的に書き直す（ファイル名は変えない。`docs/development-guide.md` がこのパスを参照するため）
- 1行目の見出しは `# planner ルール：計画単位のレビュータスクへの導入先の補足` にする
- 「## 目的」には、計画単位のレビュータスクを verifier ルール（`vault/rules/verifier/code-review.md`）の区分（Must/Should/Ask）で判定させるための導入先の補足であることを1〜2行で書く
- 「## ルール」には次の箇条をこの順で書く（文言はこのとおり。括弧内の補足は変えてよいが、引用した文字列はそのまま残す）
  - `計画単位のレビュータスクを足す条件・コードを変更するタスクの判定・title・成果物・決定済みは、` に続けて `` `.claude/agents/planner.md` の「計画単位のレビュータスク」節に従い、ここには写さない `` と書く（1文で）
  - `` 計画単位のレビュータスクの受け入れ基準の1行目は「`/code-review` で計画の差分に致命的な指摘が残っていない（`vault/rules/verifier/code-review.md` に従って判定する）」にする `` と書き、続けて理由（verifier ルールは受け入れ基準の行がそのファイルを参照している時だけ判定に使うため）を書く。この1行目の引用文はファイル内で1回だけ書く（「## 確認方法」では「上の1行目」と書き、再掲しない）
  - この行には確認コマンドを併記せず、`/code-review` の引数（`effort`・`--max-findings` など）も付けない
  - ジョブ1本の計画のタスク数は `vault/rules/planner/job-task-split.md` に従う
  - 差分の外（既存コード）への指摘を直すタスクは起こさない（verifier が対象外として reasons に残し、PR 作成時の取り出しで扱う）
- 「## 確認方法」は「計画単位のレビュータスクの受け入れ基準の1行目が上の1行目の文言である。通常のタスクの受け入れ基準には `/code-review` の行が無い」の趣旨を1〜2行で書く
- 書かない語：「コードを変えるタスク」「タスクの差分」「配下のパスと」「HARNESS_BASE_BRANCH」「merge-base」「でなく、拡張子が」は書かない（旧前提の語、またはハーネスの節の写しになるため）。コード変更の判定はハーネスに従うので、このファイルには判定を書かない
- 1ファイル100行以内（`vault/rules/README.md`）。実際は20行前後でよい

## 進捗
- 読んだルール: common/project-docs.md, creator/code-review.md, creator/skill-workflow.md
- vault/rules/planner/code-review-criterion.md を全面書き直した（約20行）
- 受け入れ基準6行の確認コマンドを実行: 出力は順に 1 / 1 / 0 / 0 / 3 / 1 で全て期待どおり
- /code-review を参照する基準は無いので実行していない
