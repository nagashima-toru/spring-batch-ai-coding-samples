# T-04 計画の差分が `/code-review` を通過する

## 目的
計画 P-20261023-sample03-tempdir-followups の全体の差分（T-01〜T-03）を `/code-review` で確かめ、致命的な指摘があれば直す。直した後も計画全体のビルド（結合テスト込み）が通ることを確かめる。

## 入力
- 計画全体の差分：`git -C <worktree のパス> diff --merge-base <ベースブランチ>`
- `vault/tasks/P-20261023-sample03-tempdir-followups/T-01.md`〜`T-03.md`（各タスクの決定済み）
- `vault/rules/verifier/code-review.md`（判定の区分）

## 成果物
- 主な成果物：計画の差分への修正（致命的な指摘が無ければ変更なし）
- 直してよいファイル（先行タスクの宣言をすべて列挙）
  - `batch-sample/src/main/java/com/example/batch/sample/job03_file_export/Sample03JobConfig.java`
  - `batch-sample/src/test/java/com/example/batch/sample/job03_file_export/Sample03JobConfigTest.java`
  - `batch-sample/docs/sample03-file-export.md`

## 受け入れ基準
- `/code-review` で計画の差分に致命的な指摘が残っていない（`vault/rules/verifier/code-review.md` に従って判定する）
- 全モジュールの静的解析と単体テストが成功する：`JAVA_HOME=/usr/lib/jvm/java-25-openjdk-amd64 ./mvnw clean verify -DskipITs -Djacoco.haltOnFailure=false 2>&1 | grep -c 'INFO. BUILD SUCCESS'` の出力が `1`
- batch-core のカバレッジ80%を含むビルドが成功する：`JAVA_HOME=/usr/lib/jvm/java-25-openjdk-amd64 ./mvnw clean verify -DskipITs -pl batch-core 2>&1 | grep -c 'INFO. BUILD SUCCESS'` の出力が `1`
- 結合テストと batch-sample のカバレッジ80%を含む全体のビルドが成功する：`JAVA_HOME=/usr/lib/jvm/java-25-openjdk-amd64 ./mvnw clean verify 2>&1 | grep -c 'INFO. BUILD SUCCESS'` の出力が `1`
- `Sample03JobConfigTest` のテストが10件実行されている（4行目のビルドの後に確認）：`grep -c 'testcase name=' batch-sample/target/surefire-reports/TEST-com.example.batch.sample.job03_file_export.Sample03JobConfigTest.xml` の出力が `10`
- 旧い説明（「省略時も csv」「未指定・空・」）がリポジトリのコードと文書に残っていない：`grep -rn -e '省略時も csv' -e '未指定・空・' batch-sample/src batch-sample/docs docs README.md` の出力が空

## 決定済み
- レビューの範囲は、ベースブランチ（`HARNESS_BASE_BRANCH`。前後の空白を除いて空なら `main`）との分岐点からの計画全体の差分（`git -C <worktree のパス> diff --merge-base <ベースブランチ>`）とする
- 計画一式4種（`vault/plans/`・`vault/tasks/`・`vault/verdicts/`・`vault/log/`）はレビューの対象にしない
- 致命的な指摘が無ければ成果物を変えず、「進捗」への記録だけでよい（「進捗」の追記が収集コミットになるので、新規コミット無しの blocked にはならない）
- 差分の外（既存コード）への指摘・致命的でない指摘・設計や仕様の変更が要る指摘の扱いは、`.claude/agents/creator.md`・`.claude/agents/verifier.md` の「コードレビューを参照する基準」の節に従う
- `/code-review` の引数（`effort`・`--max-findings` など）は付けない（`vault/rules/planner/code-review-criterion.md`）
- 方式の判断（空白だけの値が別の JobInstance になる点は解消せず文書に明記する、`format` の空白だけの値は csv として扱う）は計画票の「分割方針」で決めたもので、レビューの指摘で覆さない。覆す必要があると判断した時は、直さずに「進捗」と verdict の reasons に残す（人の判断が要る指摘の扱いは上の節に従う）
- 直す時も各タスクの決定済み（T-01・T-02 のテストメソッド名とテストの件数10件、T-03 の3語句を1回ずつ書くこと）を崩さない
- 4行目の `./mvnw clean verify` は結合テストに Docker を使う。この環境では dockerd が起動済み（`docker info` で確かめられる）
- 5行目の surefire の報告は、4行目の全体ビルドで作り直された後に確かめる
- 6行目の除外：`vault/` は計画一式（タスク票が旧い文言を引用している）で、マージ前に除去されるので対象にしない
- ビルドのコマンドはシェルの `JAVA_HOME` が JDK 21 を指すため、受け入れ基準のとおり `JAVA_HOME=/usr/lib/jvm/java-25-openjdk-amd64` を前に付けて実行する
