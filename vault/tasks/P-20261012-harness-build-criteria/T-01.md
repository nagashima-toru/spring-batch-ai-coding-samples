# T-01 方式設計書にジョブパラメータ検証の方針（未知のキーは個別 Validator で拒否）を書き、ORDER-001 の記述を直す

## 目的
Issue #42 の提案2の前半。Spring Batch 6 の `DefaultJobParametersValidator` は未知のキーを拒否しない（WARN のみ）ことと、拒否が必要なジョブは個別の Validator で拒否する方針を、SSoT の `docs/architecture.md` に書く。あわせて、基盤部品が未知のキーを拒否すると読める ORDER-001 詳細設計書の記述を直す。

## 決定済み
- #42 は提案2で進める（実装は変えない）。提案1（基盤部品を拒否する実装にする）を採らない理由：既存の結合テストが `AbstractJobIT#uniqueParameters()` で `testRunId` を付けて `JobInstance` を分けており、POINT-001 詳細設計書 §2 もこの挙動を前提に書いているため。人への質問で提案1になった場合はこのタスク票ごと書き直す
- §3.4 は §3.3 チャンクサイズの直後、`## 4. トランザクション方針` の前に置く。既存の節番号は変えない。本文は次の4項目の箇条書きにする（言い回しの調整はよいが、受け入れ基準で grep する2つの文言はそのまま使う）
  - 全ジョブに `JobParametersValidator` を設定し、必須・任意キーの検証は batch-core の `JobParametersValidators`（`required`・`requiredAndOptional`）を使う
  - `JobParametersValidators` の実体である Spring Batch 6 の `DefaultJobParametersValidator` は、必須キーの欠落だけを `InvalidJobParametersException` にし、未知のキーは WARN ログを出すだけで拒否しない（任意キーが空の `required` では未知のキーの検査自体を行わない）
  - 未知のキーの拒否が必要なジョブは、ジョブ側の個別の `JobParametersValidator` で拒否する（例：ORDER-001 の `OrderDailySalesJobParametersValidator`）。基盤部品を拒否する実装にしないのは、結合テストが `testRunId` などの補助キーを付けて `JobInstance` を分けているため
  - 書式・型の検査が要る時も同じ個別 Validator で行い、基盤部品の検証に委譲してから続ける
- ORDER-001.md §1.1 の「に委譲し（未知のキーも拒否される）、続けて上表の書式・型を検証する」は、「に委譲し、基盤部品が拒否しない未知のキーを許可キー以外として `InvalidJobParametersException` で拒否してから（方式設計 §3.4）、上表の書式・型を検証する」に直す。設計の中身（このクラスが未知のキーを拒否する）は実装どおりで変わらないので、設計レビューのやり直しは要らない
- ORDER-001.md §8 変更履歴の末尾に次の1行を足す：`| 2026-10-12 | 1.3 | 基盤部品の挙動の訂正（Issue #42）: §1.1 の Validator の説明を「未知のキーは基盤部品ではなくこのクラスで拒否する」に直す（実装は変えない） |`
- `docs/projects/member-point-expiry/detail-design/POINT-001.md` の変更履歴にある「「未知キーを許容しない」は誤り」は訂正の記録なので変えない（受け入れ基準の正規表現は「未知の**キー**は許容しない」で、これには当たらない）
- Javadoc（`JobParametersValidators.java`・`OrderDailySalesJobParametersValidator.java`）は T-02 で直すので、このタスクでは触らない。docs の確認範囲を `docs` に限るのはこのため（コードは T-02 の受け入れ基準で確かめる）
- ビルドは不要（docs だけの変更）
