# T-02 固定長部品の strict エンコードを StrictCharsetEncoder にまとめ、例外の文言と Javadoc の契約を直す

## 目的
Issue #92 の項目2〜4を解決する。`ByteLengthLineAggregator` と `ByteLengthLineTokenizer` に重複している「表せない文字を例外にする strict エンコード」を共通ヘルパー `StrictCharsetEncoder` にまとめ、例外の文言を値そのものを含まない形（位置とコードポイント。U+FFFD は置換文字であることを示す）に直し、両部品の Javadoc に契約を明記し、テストを足す。

## 決定済み
- ヘルパーの形：パッケージ `com.example.batch.core.item` の package-private な `final class StrictCharsetEncoder`（private コンストラクタ）に、`static byte[] encode(String text, Charset charset, String target)` を1つ置く。呼び出しのたびに `charset.newEncoder()` で新しいエンコーダを作り、`onMalformedInput`・`onUnmappableCharacter` をどちらも `CodingErrorAction.REPORT` にする（エンコーダは状態を持つので共有しない。例外の後の呼び出しやリスタート後の読み直しに前の状態を持ち越さない）。両部品の private `encode` は削除し、このヘルパーを呼ぶ。基盤部品の外から使う需要は無いので public にしない
- 例外：`CharacterCodingException` を捕まえたら、`text` をコードポイント単位で先頭から調べ、最初に表せない文字（対になっていないサロゲートを含む）の1始まりの位置（コードポイント単位で数える）とコードポイントで `BusinessException` を送出する（`cause` に元の例外を渡す）。文言は `"%s: 文字コード %s で表せない文字があります（位置=%d 文字=U+%04X）".formatted(target, charset.name(), 位置, コードポイント)`。コードポイントが U+FFFD の時だけ、末尾に `。U+FFFD は読込時に文字コードで解釈できなかったバイト列を置き換えた文字です` を足す。位置が見つからない時（起きない想定）は `"%s: 文字コード %s で表せない文字があります".formatted(target, charset.name())` にする
- `target` は、`ByteLengthLineTokenizer` では `入力の行`、`ByteLengthLineAggregator` では `"出力のフィールド index=" + i`（i は今と同じ0始まりの添字）。例：`入力の行: 文字コード windows-31j で表せない文字があります（位置=2 文字=U+20BB7）`
- 値（行・フィールド値）をメッセージに含めない理由：メッセージは `ErrorRecordSkipListener` の WARN ログ（`reason=`）と `LoggingJobExecutionListener` の ERROR ログに出る。方式設計 §8 は個人情報・機密情報のログ出力を禁止している。元のレコードは `ErrorRecordSkipListener` がエラーレコードファイルに書くので、位置とコードポイントがあれば復旧できる
- 変えるのは表せない文字の文言だけ。バイト長の超過（`value=`）・バイト長の不一致と境界の分断（`line=`）の文言は Issue #92 の項目3の対象外なので変えない（計画票の「次フェーズの候補」に書いた）
- Javadoc の契約：両クラスのクラス Javadoc の、表せない文字の説明の段落を次の内容に書き直す。「文字コードで表せない文字（対になっていないサロゲートを含む）を含む場合は `BusinessException` を送出する（`{@link BusinessException}` と書く）。例外のメッセージには値を含めず、1始まりの文字位置とコードポイント（U+XXXX）を示す。読込時に文字コードとして解釈できなかったバイト列は U+FFFD に置き換わって渡ってくるので、U+FFFD を表せない文字コード（Shift_JIS・Windows-31J など）では、その旨を添えた例外になる。U+FFFD を表せる文字コード（UTF-8 など）では、この置換は検出しない」。`例外のメッセージには値を含めず` の語句は各クラスに1回だけ書く
- `batch-sample/docs/sample03-file-export.md` の62行目の「出力文字コードで表せない文字を含む値は `BusinessException` で失敗する（`ByteLengthLineAggregator`）」の後ろに「例外のメッセージには値を含めず、フィールドの添字・文字位置・コードポイント（例 U+20BB7）を示す」を足す。`例外のメッセージには値を含めず` はこのファイルに1回だけ書く
- テスト（メソッド名は日本語「条件＿期待結果」。`docs/coding-standards.md` §7）：
  - `StrictCharsetEncoderTest`（新規）に次の4つを置く：`表せる文字だけの場合＿文字コードのバイト列を返す`・`表せない文字を含む場合＿位置とコードポイントを示し値を含まないBusinessExceptionをスローする`（Windows-31J で `"A𠮷B"`。メッセージに `位置=2 文字=U+20BB7` を含み、`𠮷` を含まない）・`置換文字を含む場合＿読込時の置換であることを示すBusinessExceptionをスローする`（Windows-31J で U+FFFD を含む文字列。文字列は `"A" + (char) 0xFFFD + "B"` のように組み立てる。メッセージに `U+FFFD` と `置き換えた文字` を含む）・`対になっていないサロゲートを含む場合＿BusinessExceptionをスローする`（`"A" + (char) 0xD842 + "B"` など）
  - `ByteLengthLineTokenizerTest`：既存の `表せない文字を含む行の場合＿BusinessExceptionをスローする` に、メッセージが `入力の行` と `位置=2 文字=U+20BB7` を含み、`A𠮷B` を含まないことの検証を足す。`表せない文字で例外になった後に続けて呼んだ場合＿正しく分割する` を足す
  - `ByteLengthLineAggregatorTest`：既存の `表せない文字を含むフィールド値の場合＿BusinessExceptionをスローする` の `.hasMessageContaining("A𠮷B")` を `doesNotContain` 相当（値を含まない）の検証に替え、`index=0` と `U+20BB7` を含むことを検証する。`表せない文字で例外になった後に続けて呼んだ場合＿正しく連結する` を足す
  - `FixedLengthItemReaderFactoryTest`：`解釈できないバイト列を含む行からリスタートした場合＿置換文字を示すBusinessExceptionを原因とする例外になる` を足す。Windows-31J の固定長ファイルの2行目に、Windows-31J として解釈できないバイト列（例：`0x81 0x20`。デコードすると U+FFFD と半角スペースになることを計画作成時に確かめた）を含め、1行目を読み終えた位置を持つ `ExecutionContext`（`FlatFileItemReader` の `<name>.read.count` に `1`）で `open` して `read` すると、`FlatFileParseException` が送出され、その原因が `BusinessException` で、メッセージに `U+FFFD` を含むことを確かめる。テストデータのバイト列はテストの中でバイト配列として組み立てる（ソースに不可視文字・Unicode エスケープを書かない）
- ツールの入力にバックスラッシュ・`u`・4桁の16進を書くと、ツールに渡る前にその1文字に変わることがある（計画作成時に確かめた）。テストの U+FFFD・サロゲートは上のとおり `(char) 0xFFFD` などで組み立て、Unicode エスケープを書かない
- `ByteLengthLineTokenizer` の境界の分断の検査（デコード→再エンコードの比較）は今のまま（`getBytes` を使う。strict エンコードの重複ではない）
- ORDER-001 の詳細設計書は変えない（ORDER-001 は固定長部品を使わない）
- ビルドは Java 25 が要る。この環境の既定の `JAVA_HOME` は Java 21 なので、確認コマンドの先頭の `JAVA_HOME=/usr/lib/jvm/java-25-openjdk-amd64` を付けて実行する。受け入れ基準の最後の行は、その前の `-pl batch-core` のビルドが作った surefire のレポートを読む（ビルドの後に確かめる）
