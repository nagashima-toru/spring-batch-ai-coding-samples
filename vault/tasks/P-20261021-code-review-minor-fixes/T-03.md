## 決定済み
- 項目5の方針（解決のタイミングは変えない）：入れ子の例外は、遅延解決（`@JobScope` の Bean を Step の Bean の生成時に作る）の中で `resolve` が失敗した時に出る。`resolve` が失敗しうる入力は `scheduledTime`（`OffsetDateTime.parse`）・`targetDate`（型）・`inputFile`・`errorFile`（`Path.of` の `InvalidPathException`。Linux ではヌル文字を含む時）で、前の2つは Validator が検証済み。残りの2つも Validator で検証すれば、不正なパラメータはすべて起動時に `InvalidJobParametersException`（入れ子でない）になり、Bean の生成では失敗しない。解決を `JobExecutionListener#beforeJob` などに前倒しする案は、値の受け渡しを `ExecutionContext` 経由に変えることになり 1.6 版の方式（Issue #75）から外れるので採らない
- Validator：`inputFile`・`errorFile` が指定された時、値を `String.valueOf(parameter.value())` で文字列にして `Path.of` に渡し、`InvalidPathException` なら `InvalidJobParametersException` を送出する。文言は `"inputFile はパスとして解釈できる文字列で指定してください: " + e.getMessage()`（errorFile も同じ形で、キー名だけ替える）。型の検査は足さない（`@Value` の String への変換に任せる今の動きのまま）。検証の順は、未知のキー → scheduledTime → targetDate → inputFile → errorFile。クラス Javadoc の検証項目の説明にもパスの検証を足す
- これは挙動の変更（ヌル文字を含むパスが、Step 1 の Bean の生成での入れ子の例外から、起動時の `InvalidJobParametersException` に変わる）。どちらも終了コード1で、運用の扱いは同じ
- Holder（項目6）：コードは変えず、クラス Javadoc に次の2文を足す。「スコーププロキシは CGLIB でこのクラスを継承して作り、Objenesis でコンストラクタを呼ばずに生成されるため、引数なしコンストラクタは不要」「resolve の入力はすべて起動前に Validator が検証するので、Bean の生成（Step の実行中の遅延解決）で不正なパラメータの例外は起きない」。`Objenesis でコンストラクタを呼ばずに生成される` と `resolve の入力はすべて起動前に Validator が検証する` の語句はそれぞれ1回だけ書く。根拠：Spring の CGLIB プロキシ（`ObjenesisCglibAopProxy`）は Objenesis でインスタンスを作り、コンストラクタを呼ばない。ORDER-001 の結合テストはこのプロキシ経由でジョブを完走しており、今の動作が正しいことは確かめ済み（T-04 でプロキシであることのテストを足す）
