# T-01 CsvHeaderCheckTasklet の BOM 定数とテストの BOM を Unicode エスケープ表記にする

## 目的
Issue #92 の項目1を解決する。`CsvHeaderCheckTasklet` の BOM 定数と、そのテストの BOM 付きの文字列が、ソース中にリテラルの U+FEFF（不可視文字）で書かれているのを、Java の Unicode エスケープ（バックスラッシュ・`u`・`FEFF` の6文字）の表記にする。リポジトリにリテラルの U+FEFF を含むファイルが残らないようにする。

## 入力
- `batch-core/src/main/java/com/example/batch/core/tasklet/CsvHeaderCheckTasklet.java`（52行目の `BOM` 定数がリテラルの U+FEFF）
- `batch-core/src/test/java/com/example/batch/core/tasklet/CsvHeaderCheckTaskletTest.java`（`BOM付きファイルの場合＿…`・`BOM付きで項目名が異なる場合＿…` の2テストの文字列の先頭がリテラルの U+FEFF）
- `docs/coding-standards.md`（コーディング規約）、`CLAUDE.md` の「禁止事項」

## 成果物
- 主な成果物：`batch-core/src/main/java/com/example/batch/core/tasklet/CsvHeaderCheckTasklet.java` の `BOM` 定数の表記（1ファイル）
- 付随して変えるファイル：`batch-core/src/test/java/com/example/batch/core/tasklet/CsvHeaderCheckTaskletTest.java`

## 受け入れ基準
- リポジトリ（`.git`・`target`・`vault` を除く）にリテラルの U+FEFF（UTF-8 のバイト列 EF BB BF）を含むファイルが無い：`grep -rlP '\xEF\xBB\xBF' --exclude-dir=.git --exclude-dir=target --exclude-dir=vault .` の出力が空
- `CsvHeaderCheckTasklet.java` の `BOM` 定数が Unicode エスケープで書かれている：`grep -c 'String BOM = ..uFEFF.;' batch-core/src/main/java/com/example/batch/core/tasklet/CsvHeaderCheckTasklet.java` が `1`
- テストの BOM 付きの2つの文字列が Unicode エスケープで書かれている：`grep -c 'uFEFForder_no,line_no,' batch-core/src/test/java/com/example/batch/core/tasklet/CsvHeaderCheckTaskletTest.java` が `2`
- 全モジュールの静的解析と単体テストが通る：`JAVA_HOME=/usr/lib/jvm/java-25-openjdk-amd64 ./mvnw clean verify -DskipITs -Djacoco.haltOnFailure=false 2>&1 | grep -c '^.INFO. BUILD SUCCESS'` が `1`
- batch-core のカバレッジ80%を含めて通る：`JAVA_HOME=/usr/lib/jvm/java-25-openjdk-amd64 ./mvnw clean verify -DskipITs -pl batch-core 2>&1 | grep -c '^.INFO. BUILD SUCCESS'` が `1`
- 直前のビルドで BOM 付きの2テストが実行された（BOM が U+FEFF として比較されている）：`grep -c 'testcase name=.BOM付き' batch-core/target/surefire-reports/TEST-com.example.batch.core.tasklet.CsvHeaderCheckTaskletTest.xml` が `2`

## 決定済み
- 定数は `private static final String BOM = "\uFEFF";` と書く（Javadoc の `/** 先頭に付く BOM（U+FEFF）。 */` はそのまま）。Unicode エスケープは Java のコンパイル時に U+FEFF の1文字になるので、動作は変わらない
- テストの2つの文字列は、先頭のリテラルの U+FEFF を Unicode エスケープに置き換えて `"\uFEFForder_no,line_no,quantity\n"`・`"\uFEFForder_no,line_no,qty\n"` と書く。テストメソッドの名前と検証内容は変えない（テストの追加はしない）
- 書き方の注意：ツール（Write・Edit・Bash）の入力にバックスラッシュ・`u`・4桁の16進を書くと、ツールに渡る前に U+FEFF の1文字に変わることがある（計画作成時に確かめた。Issue #92 の元の不具合もこの経路と考えられる）。Edit で直さず、`perl -i -pe 's/\xEF\xBB\xBF/\x5CuFEFF/g' <ファイル>` で2ファイルのリテラルの U+FEFF をエスケープの6文字に置き換える（`\x5C` がバックスラッシュ。この形ならツールの入力に Unicode エスケープが現れない）。置き換えた後に受け入れ基準の1〜3行目を実行して確かめる
- Checkstyle（`config/checkstyle/checkstyle.xml`）に Unicode エスケープを禁止する規則（AvoidEscapedUnicodeCharacters）は無いので、そのまま使ってよい
- 確認の範囲はリポジトリ全体。除くのは `.git`、ビルド出力の `target`（生成物で、ソースを直せば次のビルドで作り直されるため）、`vault`（計画一式は PR の前に除去され、verdict や「進捗」の記録にツールの入力の変換でリテラルの U+FEFF が入りうるため。成果物ではない）。計画作成の時点でリテラルの U+FEFF を含むのはこの2ファイルだけ。「進捗」に書く時も Unicode エスケープの6文字は書かない
- 受け入れ基準の最後の行は、その前の `-pl batch-core` のビルドが作った surefire のレポートを読む（ビルドの後に確かめる）
- ビルドは Java 25 が要る。この環境の既定の `JAVA_HOME` は Java 21 なので、確認コマンドの先頭の `JAVA_HOME=/usr/lib/jvm/java-25-openjdk-amd64` を付けて実行する
- ORDER-001 の詳細設計書は変えない（BOM を除いて照合する仕様は 1.5 版で書き済みで、表記の変更は設計に影響しない）
