# T-04 OrderDailySalesJobIT のログ回数の検証を ListAppender にし、パラメータ検証とプロキシのテストを足す

## 目的
Issue #92 の項目7を解決し、項目5・6の結論を結合テストで確かめる。`OrderDailySalesJobIT` の「実行時パラメータ確定のログが1回だけ出る」検証を、標準出力の取り込み（`CapturedOutput` の文字列の分割）ではなく、ロガーに付けた Logback の `ListAppender` でそのテストのイベントだけを数える形にする。T-03 で足したパスの検証が起動時に入れ子でない例外になることと、実行時パラメータの Bean がクラスプロキシであることのテストを足す。

## 決定済み
- ログ回数の検証（項目7）：テストメソッド名 `正常に実行した場合＿実行時パラメータ確定のログは1回だけ出力される` は変えず、引数の `CapturedOutput` を外す。`LoggerFactory.getLogger(OrderDailySalesJobConfig.class)` を `ch.qos.logback.classic.Logger` にキャストして `ListAppender<ILoggingEvent>` を付け、ジョブの実行後に `finally` で `detachAppender` する（`OrderDetailWorkClearTaskletTest` と同じ書き方）。数えるのは、`ILoggingEvent#getMessage()`（引数を埋める前のテンプレート）が `実行時パラメータを確定しました: ` で始まり、かつ `getFormattedMessage()` がそのテストの入力ファイルのパス（`input.toString()`。`@TempDir` の下なのでテストごとに一意）を含むイベントで、件数が `1` であることを確かめる。理由：出力の書式（JSON・テキスト）や他のテスト・他のスレッドの出力に左右されない
- `@ExtendWith(OutputCaptureExtension.class)` と、`CapturedOutput`・`OutputCaptureExtension`・`ExtendWith` の import は、使う所が無くなるので削除する
- パス不正のテストを足す：`inputFileがパスに変換できない場合＿ジョブパラメータ検証エラーで起動失敗し本テーブルは変わらない`。`insertOldData()` の後、`inputFile` をヌル文字を含む文字列（`"in" + (char) 0 + "put.csv"` のように組み立てる）にしたパラメータ（`scheduledTime` は `nextScheduledTime()`）で `jobOperator.start` を呼び、`assertThatThrownBy(...).isInstanceOf(InvalidJobParametersException.class)` と、本テーブルが `OLD_DETAIL`・`OLD_SALES` のままであることを確かめる（既存の `scheduledTimeを渡さない場合は…` と同じ形）。Spring Batch 6.0.5 の `TaskExecutorJobLauncher` は、JobInstance を作った後、JobExecution（ジョブパラメータの保存）を作る前に Validator を呼ぶことを計画作成時に確かめた（ヌル文字は DB に保存されない）
- プロキシのテストを足す：`実行時パラメータのBeanを取得した場合＿CGLIBのクラスプロキシである`。`ApplicationContext` を `@Autowired` し、`getBean("orderDailySalesRunParameters")` が `OrderDailySalesRunParametersHolder` のインスタンスで、`org.springframework.aop.support.AopUtils.isCglibProxy` が `true` であることを確かめる（ジョブのスコープの外では `get()` を呼ばない。プロキシの取得だけならスコープは要らない）。引数なしコンストラクタが無くてもプロキシが作れること（項目6）を示すテストになる
- ツールの入力にバックスラッシュ・`u`・4桁の16進を書くとその1文字に変わることがあるので、Unicode エスケープは書かない（ヌル文字は `(char) 0` で組み立てる）
- 既存の他のテストは変えない。テストメソッド名は日本語「条件＿期待結果」（`docs/coding-standards.md` §7）
- 本番コード・設計書は変えない（設計書の §7 は T-03 で直し済み。食い違いがあれば設計書を正とする）
- ビルドは Java 25 が要る。この環境の既定の `JAVA_HOME` は Java 21 なので、確認コマンドの先頭の `JAVA_HOME=/usr/lib/jvm/java-25-openjdk-amd64` を付けて実行する。Docker デーモンは起動済みで、結合テスト（Testcontainers）を実行できる
- 受け入れ基準のビルドは書いた順に実行する（`clean` が `target` を消すため）。最後の行は、その前の `./mvnw clean verify` が作った failsafe のレポートを読む
