# T-06 `ValidatingItemProcessorBase` 派生の具象型を `@StepScope` の Bean にする書き方を ArchUnit で検出する

## 目的
T-02 で `ValidatingItemProcessorBase.process()` を final に戻した結果、`ValidatingItemProcessorBase` を継承した Processor を、Bean メソッドの戻り値を具象型にして `@StepScope` の Bean にすると、スコーププロキシがクラスのプロキシになり、実行時に NullPointerException になる（`docs/decisions.md`）。今は `orderDailySalesProcessor` の1つだけがインタフェース型で正しいが、今後の案件で具象型の Bean を足されても検出できない。T-05 の `/code-review` の指摘（人の判断：B）に従い、この書き方を ArchUnit のテストでビルド時に止める。あわせて `docs/decisions.md` の旧行と新行が矛盾して読める点を整理する。

## 決定済み
- ルールの内容：`@Bean` かつ `@StepScope` のメソッドで、戻り値の型（`haveRawReturnType`）が `ValidatingItemProcessorBase` に代入可能（`assignableTo`）なものを違反とする。つまり「`ValidatingItemProcessorBase` 派生の具象型を返す `@StepScope` の Bean メソッド」だけを止める。戻り値が `ItemProcessor<I, O>` なら違反にしない。Reader・Writer・Tasklet など他の `@StepScope` の Bean は対象外（具象型の Bean が既にあり、final のメソッドを持たないため問題にならない）
- 検査の範囲：`com.example.batch` 配下のうち、`batch-sample` のテストのクラスパスにある main のクラス（`ImportOption.DoNotIncludeTests`）。`batch-core` のテストには置かない（`batch-core` から `batch-sample` の Config は見えないため。`batch-sample` なら全ジョブの Config を検査できる）
- テストは `@AnalyzeClasses(packages = "com.example.batch", importOptions = ImportOption.DoNotIncludeTests.class)` と `@ArchTest` の static フィールドまたはメソッドで書いてよい。ただし、メソッド名は日本語（条件＿期待結果）とし、受け入れ基準の2つの名前で grep できるようにする。`@ArchTest` を使うとメソッド名で grep できない場合は、通常の `@Test` で `ClassFileImporter` を使って書く
- 負のテスト：同じテストクラスの中に、違反の見本として `ValidatingItemProcessorBase` を継承した具象クラスを返す `@Bean @StepScope` のメソッドを持つ入れ子の static クラス（テスト専用）を置き、`ClassFileImporter().importClasses(...)` で取り込んだ上で、ルールの `check` が `AssertionError` を投げることを AssertJ の `assertThatThrownBy` で確かめる。見本のクラスは main の検査（`DoNotIncludeTests`）には入らないので、本番の検査は落ちない
- 依存：`com.tngtech.archunit:archunit-junit5`、スコープは test。バージョンは親 POM の `properties` に `archunit.version` を足し、`dependencyManagement` で管理する（各モジュールにバージョンを書かない。CLAUDE.md の禁止事項）。バージョンは、Java 25 のクラスファイル（バージョン 69）を読める最新の安定版を選ぶ。Maven Central に出ている版を確認して決め、選んだ版と理由を「進捗」に書く
- ArchUnit が Java 25 のクラスファイルを読めずに失敗する時（`UnsupportedClassVersionError` や取り込みの失敗）は、版を上げても解消しないなら blocked にし、question に失敗の要点を書く。ArchUnit を使わない形（Checkstyle の独自ルールなど）への切り替えは、勝手に決めない
- `docs/decisions.md`：12 行目の「`@StepScope` で生成する Bean のクラスは final にせず…（`ValidatingItemProcessorBase#process` は例外。Issue #76 で final に戻した。末尾の行を見る）」は、矛盾して読めないように書き直す。規則そのものは「`@StepScope` で生成する Bean のクラスは final にしない。継承元の public メソッドも final にしない」のまま残し、例外は「`ValidatingItemProcessorBase` を継承する Processor は `process()` が final のため、Bean メソッドの戻り値と注入先の型を `ItemProcessor<I, O>` にする（docs/architecture.md §13）」と1か所に書く。「Issue #76 で final に戻した。末尾の行を見る」の言い回しは残さない。末尾の Issue #76 の行には「具象型で `@StepScope` の Bean にする書き方は `StepScopeBeanRuleTest`（ArchUnit）がビルド時に検出する」を足す
- `docs/architecture.md` §13：T-01 で足した項目に「具象型で宣言すると `batch-sample` の `StepScopeBeanRuleTest` が失敗する」旨を1文足す。T-01 で足した文は消さない
- 新しいファイル `batch-sample/src/test/java/com/example/batch/sample/architecture/StepScopeBeanRuleTest.java` のパスをバッククォートで書く参照は、この T-06 の成果物の中（`docs/architecture.md`・`docs/decisions.md`）にだけ入れる
- `./mvnw clean verify` は JDK 25（`JAVA_HOME=/usr/lib/jvm/java-25-openjdk-amd64`）と Docker（`postgres:16` のイメージがローカルにある）が要る。使えない時は基準を満たせないので blocked にし、question にその旨を書く
- Checkstyle・SpotBugs（`config/checkstyle/`）がテストコードにも掛かる場合は、規約に従う。基準を緩める設定の変更はしない
