# T-04 sample05 に AbstractApiCallTasklet の件数取得 Step と 5xx 異常終了の結合テストを追加する

## 目的
T-03 で改訂した解説どおりに、sample05 の取込 Step の前に `AbstractApiCallTasklet` を継承した件数取得 Step（`sample05.00UserCountStep`）を追加する。あわせて、API が 5xx を返し続けると `BatchHttpClient` のリトライの後に `RetryableSystemException` で異常終了することを結合テストで確かめる。

## 決定済み
- 解説（`batch-sample/docs/sample05-api-import.md`）は T-03 で確定済みなので変えない。解説と食い違う実装が必要になったら blocked にする
- `ApiUserCountResponse`：`public record ApiUserCountResponse(long count)`（Javadoc 付き）
- `ApiUserCountTasklet`：`public class ApiUserCountTasklet extends AbstractApiCallTasklet<ApiUserCountResponse>`。コンストラクタは `(BatchHttpClient httpClient, String baseUrl, String token)`。`callApi` は `client.get(baseUrl + "/users/count", ApiUserCountResponse.class, Map.of("Authorization", "Bearer " + token))`。`handleResponse` はレスポンスが null なら `SystemException`（メッセージ例「件数APIのレスポンスが空です」）を投げ、そうでなければ件数を INFO ログに出し、`contribution.getStepExecution().getExecutionContext().putLong("apiUserCount", response.count())` で保存する。HTTP の例外変換・リトライは `BatchHttpClient` に任せ、Tasklet では catch しない
- `Sample05JobConfig`：
  - 新規 Step の名前は `sample05.00UserCountStep`（既存の `sample05.01ImportStep` は改名できず、その前に入るため `00`）、Bean 名は `sample05UserCountStep`。Tasklet の Bean は `sample05UserCountTasklet`（`SampleProperties` の `job05().api()` の `baseUrl()`・`token()` を渡す。シングルトンでよい）。Step は `.tasklet(tasklet, transactionManager)` と `loggingStepExecutionListener` で組む
  - ジョブは `.start(sample05UserCountStep).next(sample05ImportStep)`（T-05 で Decider を前に入れる。このタスクでは直列でよい）
  - ジョブ名 `sample05ApiImportJob`・`sample05.01ImportStep`・既存の Bean 名（`sample05ImportStep`・`sample05UserReader`・`sample05UserProcessor`・`sample05UserWriter`）・Reader 名 `sample05UserReader` は変えない
  - Batch の `faultTolerant()` は Skip のために残すが、`retry`・`retryLimit`・`retryPolicy` は呼ばない（architecture §5.2。HTTP のリトライは `BatchHttpClient` が行う）。コメントでも `.retry` と書かない（受け入れ基準の grep に当たるため。書くなら「Batch の Retry」と書く）
  - クラスの Javadoc に件数取得 Step を足す
- 単体テスト `ApiUserCountTaskletTest`（Spring コンテキストを使わず Mockito で `BatchHttpClient` をモックする）。メソッドは次の2つ（名前は受け入れ基準が照合する）:
  - `件数APIが件数を返した場合_ステップのExecutionContextにapiUserCountを保存する`：件数3を返すと `RepeatStatus.FINISHED` で、Step の ExecutionContext の `apiUserCount` が3
  - `件数APIのレスポンスが空の場合_SystemExceptionをスローする`
- 結合テスト `Sample05ApiImportJobIT`（既存の `ページングAPIから全件を取り込み正常終了する` は変えずに通す）:
  - スタブに `/users/count` のコンテキストを足す（`HttpServer` は最長一致なので `/users` と別に登録できる）。Authorization が `Bearer local-dummy-token` でなければ401、そうでなければ `{"count":3}` を返す。リクエスト数を static な `AtomicInteger`（例：`COUNT_REQUESTS`）で数える
  - 5xx の切り替え：static な `volatile boolean` のフラグ（例：`serverError`）が真の間、`/users` と `/users/count` の両方が500を返す。`@BeforeEach` でフラグを偽に、カウンタを0に戻す
  - `件数取得Stepが成功した場合_取込Stepより先に実行され件数をExecutionContextに保存する`：COMPLETED、`sample05.00UserCountStep` と `sample05.01ImportStep` が両方 COMPLETED、`sample05.00UserCountStep` の Step の ExecutionContext の `apiUserCount` が3、`sample05.00UserCountStep` の終了時刻が `sample05.01ImportStep` の開始時刻より後でない（`isAfter` が偽）
  - `APIが5xxを返し続ける場合_BatchHttpClientのリトライ後にRetryableSystemExceptionで異常終了する`：フラグを真にして起動し、`BatchStatus.FAILED`、ExitStatus の終了コードが `ExitStatus.FAILED.getExitCode()`（終了コード1に対応。architecture §7）、`execution.getAllFailureExceptions()` に `RetryableSystemException` の例外がある（原因をたどって見つかればよい）、`COUNT_REQUESTS` が3（`batch.core.http.retry.max-attempts` の既定3回まで試したこと）、`app.api_user` が0件
  - リトライ間隔は既定値（500ms→1s）のままでよい。テストでスリープしない
- Flyway のファイルは追加・変更しない。batch-core は変えない
- `./mvnw clean verify` は Docker と JDK 25 が必要。この環境では使えることをオーケストレーターが確認済み
