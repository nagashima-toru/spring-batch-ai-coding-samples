# T-02 ApiUserReadCountListener を Reader の読込位置から取得件数を求める実装に直し単体テストを書き直す

## 目的
取込 Step の取得件数 `apiUserReadCount` を、StepExecution の readCount ではなく Reader が確定させた読込位置から求めるようにし、チャンクの途中で失敗した後のリスタートで取得件数が水増しされないようにする（Issue #79。T-01 で改訂した解説に合わせる）。

## 決定済み
- `Sample05JobConfig` に定数を2つ足す：`public static final String USER_READER_NAME = "sample05UserReader";`・`public static final String USER_JSON_READER_NAME = "sample05UserJsonReader";`（Javadoc を付ける）。`sample05UserReader` Bean の `RestApiPagingItemReader` と `JsonItemReaderFactory.create` の Reader 名の文字列リテラルをこの定数に置き換える（値は変えない）
- `sample05ImportStep` のリスナー登録は `.listener(new ApiUserReadCountListener(USER_READER_NAME, USER_JSON_READER_NAME))` にする（この字面で1回だけ書く）
- `ApiUserReadCountListener` のコンストラクタは `public ApiUserReadCountListener(String... readerNames)`。引数なしのコンストラクタは残さない。`READ_COUNT_KEY = "apiUserReadCount"` は変えない
- `afterStep` の計算（T-01 の解説どおり）：
  1. Step の ExecutionContext から、渡された Reader 名の順に `<Reader名>.read.count` のキーを探し、最初に見つかったキーの値を読込位置とする。どのキーも無ければ読込位置は 0
  2. 値の読み出しは `((Number) stepContext.get(key)).longValue()` にする（Reader は int で保存するが、JobRepository からの復元後の型に依存しないため。`getLong` は使わない）
  3. `stepExecution.getStatus() == BatchStatus.COMPLETED` なら取得件数 = 読込位置 − 1（終端の null が返る読込が1件数えられるため）。それ以外（FAILED・STOPPED など）は取得件数 = 読込位置。どちらも `Math.max(0L, …)` で負にしない
  4. Job の ExecutionContext の `apiUserReadCount` に `putLong` で上書きする（前回の値に足し込まない。リスタートでは読込位置が前回から引き継がれ累計になっているため）
  5. 戻り値は今と同じ `null`
- `getReadCount`・`getReadSkipCount` はリスナーで使わない。Skip した件は読込位置に含まれるので、Skip 件数を足さない
- リスナーの Javadoc を新方式に書き直す（T-01 の解説の要点：読込位置から求める・COMPLETED 時は1を引く・上書き・readCount を使わない理由（Issue #79））。「読込件数＋読込 Skip 件数」の文言は残さない
- `ApiUserReadCountListenerTest` の既存の2件（旧方式の検証）は削除し、次の5件にする（メソッド名はこのとおり。リスナーは `new ApiUserReadCountListener(Sample05JobConfig.USER_READER_NAME, Sample05JobConfig.USER_JSON_READER_NAME)` で作る。StepExecution の状態は `setStatus(BatchStatus.…)`、読込位置は `getExecutionContext().putInt("<Reader名>.read.count", n)` で用意する）
  1. `取込Stepが完了した場合_Readerの読込位置から終端の読込1件を引いた件数を保存する`：COMPLETED、`sample05UserReader.read.count`=4、readCount=99（使われないことを示す）→ 3
  2. `inputFile指定で取込Stepが完了した場合_JSON用Readerの読込位置から件数を求める`：COMPLETED、`sample05UserJsonReader.read.count`=3 → 2
  3. `取込Stepがチャンクの途中で失敗した場合_readCountではなくコミット済みの読込位置を保存する`：FAILED、`sample05UserReader.read.count`=2、readCount=3 → 2
  4. `取込Stepが最初のチャンクで失敗した場合_読込位置が無いため0件を保存する`：FAILED、キー無し、readCount=2 → 0
  5. `リスタートで取込Stepが完了した場合_前回の件数に足し込まず読込位置から求めた件数で上書きする`：Job の ExecutionContext に `apiUserReadCount`=2 が残っている、COMPLETED、`sample05UserReader.read.count`=6 → 5
- `Sample05ApiImportJobIT` はこのタスクでは変えない（T-03 で直す）。今の結合テスト（チャンクサイズ2）は新方式でも成り立つ見込み（途中失敗の実行の読込位置2、リスタート完了時の読込位置4−1=3）だが、このタスクの基準では結合テストを実行しない
- ビルド確認の grep パターンは `vault/rules/planner/job-task-split.md` の `'^\[INFO\] BUILD SUCCESS$'` の代わりに `'^.INFO. BUILD SUCCESS'` を使う（シェルの特殊文字を避けるため。判定の意味は同じ）
- 旧方式の記述の確認範囲は `batch-sample`・`docs`（`*.java`・`*.md`）。`vault/` は計画票・タスク票が旧方式の文言を引用しているため対象外
- Spring Batch 6 の API（`org.springframework.batch.core.BatchStatus`、`org.springframework.batch.infrastructure.item.ExecutionContext`）を使う。5系のコードを流用しない
