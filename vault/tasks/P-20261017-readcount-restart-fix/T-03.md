# T-03 Sample05ApiImportJobIT にチャンク途中失敗のリスタートテストを追加しスタブのページ判定を正確にする

## 目的
チャンクの途中で失敗した後のリスタートでも取得件数が水増しされず、件数突き合わせ（`sample05.02CountCheckStep`）が通ることを実 DB の結合テストで確かめる。あわせて、スタブのページ判定 `query.contains("page=1")` が page=10 以降にも一致する点を、クエリパラメータの正確な判定に直す（Issue #79）。

## 決定済み
- 基準は上から順に確かめる。2・3行目は1行目の `./mvnw clean verify` が作った failsafe のレポートを読む（6行目の `clean` でレポートが消えるため、6・7行目より前に確かめる）
- `@DynamicPropertySource` の設定：`sample.job05.api.page-size` は 2 のまま、`sample.chunk-size` を `() -> 3` にする（`registry.add("sample.chunk-size", () -> 3);` の形で1回だけ書く）。コメントを「チャンクの途中でページの取得が起きるよう、チャンクサイズ（3）をページサイズ（2）と異なる値にする」の趣旨に直す
- スタブのユーザーを5件・3ページにする：page=0 は U001 山田・U002 鈴木（今のまま）、page=1 は U003 佐藤（今のまま）と U004 高橋（`u004@example.com`）、page=2 は U005 田中（`u005@example.com`）、それ以外のページは `[]`。ページサイズ2なので page=2 の1件で最終ページになる
- ページ番号の判定：クエリ文字列を `&` で分け、各要素を最初の `=` で名前と値に分け、名前が `page` の値を `Integer.parseInt` で得る private static メソッド（例：`pageParam(String query)`。`page` が無ければ -1）を作り、スタブの分岐はこの戻り値の一致で行う。`query.contains("page=…")` の形は残さない
- 失敗を注入するフラグは `secondPageError`（boolean）をやめ、`private static volatile int errorPage;`（このページ番号の時だけユーザーAPIが500を返す）にする。`setUp` で `-1` に戻す
- `reportedCount` の既定値（`setUp`）を 5 にする。既存テストの件数の期待値を 3 から 5 に直す（`ページングAPIから全件を取り込み正常終了する` の件数、`件数取得Stepが成功した場合_…` の `apiUserCount`、`件数APIの件数と取得件数が一致しない場合_…` の取込件数）。`件数APIの件数と取得件数が一致しない場合_…` は `reportedCount = 6` にし、コメントを「ユーザーAPIは5件しか返さない」に直す
- 既存テスト `取込Stepが途中で失敗した場合_リスタートで続きを取り込み件数の突き合わせも通る`（メソッド名は変えない）は `errorPage = 2` にする（1チャンク目の U001〜U003 をコミットした後、2チャンク目で U004 を読んだ後の page=2 の取得で失敗する）。期待値：失敗した実行の取込 Step の writeCount が 3、リスタートの取込 Step の readCount が 2、`apiUserReadCount` が 5、件数突き合わせ Step が COMPLETED、`app.api_user` が5件。コメントも合わせて直す
- 新しいテストのメソッド名は `チャンクの途中で失敗した場合_リスタート後の取得件数が水増しされず件数の突き合わせが通る`。手順と期待値：`errorPage = 1` で起動 → FAILED、取込 Step の writeCount が 0、失敗した Job の ExecutionContext の `apiUserReadCount` が 0。続けて取込 Step の readCount が 2 であることを assert し、「Spring Batch 6 では失敗した実行の readCount にロールバックしたチャンクの読込件数も入る（Issue #79 の再現）」の趣旨のコメントを付ける。`errorPage = -1` に戻して `jobOperator.restart(failed)` → COMPLETED、取込 Step の readCount が 5、`apiUserReadCount` が 5、件数突き合わせ Step が COMPLETED、`app.api_user` が5件
- 失敗した実行の readCount が 2 にならなかった場合（再現しなかった場合）は、その assert を外し、観測した値と「再現しなかった」ことをテストのコメントとタスク票の「進捗」に書く。リスタート後の期待値（取得件数5・突き合わせ COMPLETED）はそのまま確かめる
- 既存テスト `inputFileを指定した場合_APIを呼ばずJSONファイルから取り込む` に、Job の ExecutionContext の `apiUserReadCount` が 2 であることの assert を足す（JSON 用 Reader `sample05UserJsonReader` の読込位置から求めていることの確認）
- その他の既存テスト（5xx・存在しないファイル）は期待値を変えない。`COUNT_REQUESTS` が 3 の assert もそのまま
- page=10 以降を実際に要求するテストは足さない（判定を正確にするだけ）
- リスナー・`Sample05JobConfig`・解説はこのタスクでは変えない。結合テストが新方式で通らない場合は、リスナーを直さずに blocked にして理由を question に書く
- ビルド確認の grep パターンは `vault/rules/planner/job-task-split.md` の `'^\[INFO\] BUILD SUCCESS$'` の代わりに `'^.INFO. BUILD SUCCESS'` を使う（シェルの特殊文字を避けるため。判定の意味は同じ）
- Testcontainers は2系（`org.testcontainers.postgresql.PostgreSQLContainer`）を `AbstractJobIT` 経由で使う。テストの基底クラスは変えない
