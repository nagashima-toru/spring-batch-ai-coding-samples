# システムテストシナリオ: お知らせ通知バッチ（announcement-notification）

| 項目 | 内容 |
|---|---|
| 対象ジョブ | ANNOUNCE-001 announcementNotifyJob |
| 実施環境 | ローカル（Docker Compose PostgreSQL 16、プロファイル local） |
| 実施期間 | 2026-08-09 |
| 入力設計書 | basic-design.md（1.1版）／detail-design/ANNOUNCE-001.md |

## 実行方法（共通）

```bash
docker compose -f docker/compose.yaml up -d          # ローカルDB
./mvnw -q package -pl batch-sample -am -DskipTests    # jar ビルド
java -jar batch-sample/target/batch-sample-0.1.0-SNAPSHOT.jar \
  --spring.batch.job.name=announcementNotifyJob \
  scheduledTime=2026-08-09T09:15:00,java.time.LocalDateTime \
  errorFile=/tmp/announce_error.txt
echo "exit=$?"    # 0=正常 / 2=警告 / 1=異常
```

- 定期ポーリング運用のため、通常実行は `scheduledTime` を実行ごとに変えて起動する（JobInstance を分ける）。
- **リラン（ST-4）は、異常終了時と識別パラメータ（`scheduledTime` と `errorFile` の両方）を完全に一致させて再起動する**。
  どちらか一方でも変えると Spring Batch は別 JobInstance と判定し、リスタート（失敗Stepからの再開）ではなく
  新規実行（全Step再実行）になる。この場合、Step2 で先に flag 済みの区域エラー（status=9）は再カウントされず
  0 になるため、区域展開不能の警告終了が失われる（実施時に確認。運用手順書へ明記する）。
- データ生成: `data/reset.sql`（初期化）／`data/functional_seed.sql`（ST-1〜3）／`data/generate_perf_data.sql`（ST-6）。

## シナリオ詳細

### ST-1: 通知対象抽出の正常系

- **目的**: 業務ルール（本人＝区域内住所、家族＝住所なし同居、区域外/メール未設定の除外）どおりに通知対象が確定し、メール送信テーブルへ登録され、お知らせが処理済みになること。
- **事前条件**: `reset.sql` → `functional_seed.sql`。お知らせ1（区域13101）・ユーザー101〜105。ただし ST-1 では Skip を発生させないため、事前に形式不正ユーザー105を除外（`DELETE FROM app.app_user WHERE user_id=105`）し、区域不正のお知らせ2も除外（`UPDATE app.announcement SET status='2' WHERE announcement_id=2`）してお知らせ1のみ対象にする。

| # | 操作 | 期待結果 |
|---|---|---|
| 1 | ジョブ起動 | 終了コード0（COMPLETED） |
| 2 | `mail_send` 件数・宛先 | 2件（user_id=101本人, 102同居家族）。103区域外・104メール未設定は含まれない |
| 3 | `mail_send` の内容 | subject=お知らせtitle, body=お知らせbody, send_status='0' のスナップショット |
| 4 | `announcement` 状態 | announcement_id=1 が status='2'、processed_at 設定あり |

- **確認ポイント**: 対象ユーザーIDの一致、スナップショット値、処理済み更新。
- **実施結果**: OK
- **証跡**: exit=0 / mail_send=2件（101,102）/ announcement.status=2

### ST-2: 警告終了（Skip）と手動リカバリ運用

- **目的**: メール形式不正ユーザーが Skip されエラーレコードファイルへ退避され、警告終了（2）となること。運用手順（ファイル確認→データ修正→再取込）で最終的に全対象が通知されること。
- **事前条件**: `reset.sql` → `functional_seed.sql`。お知らせ2は対象外化（status='2'）。ユーザー105（形式不正メール、区域内13101の zip_code=1000002）を残す。

| # | 操作 | 期待結果 |
|---|---|---|
| 1 | ジョブ起動 | 終了コード2（COMPLETED_WITH_WARNING） |
| 2 | エラーファイル内容 | `1,105,invalid-mail<TAB>入力チェックエラー...` の行がある |
| 3 | `mail_send` 件数 | 正常ユーザー分のみ（105は含まれない） |
| 4 | リカバリ: 105のメールを修正→お知らせを未処理へ戻し再実行 | 終了コード0、105が追加登録、既存分は重複しない |

- **確認ポイント**: 終了コード2、エラーファイルのキー・理由、冪等な再取込。
- **実施結果**: OK
- **証跡**: exit=2 / error.txt に user_id=105 の行 / リカバリ後 exit=0・重複なし

### ST-3: 警告終了（区域展開不能）と区域修正運用

- **目的**: 区域が郵便番号マスタに展開できないお知らせが status='9' にエラー化され、他のお知らせは処理継続、警告終了（2）となること。区域修正→未処理へ戻し再実行で完了できること。
- **事前条件**: `reset.sql` → `functional_seed.sql`。お知らせ1（正常）とお知らせ2（区域99999＝マスタになし）。Skip を避けるため形式不正ユーザー105は削除。

| # | 操作 | 期待結果 |
|---|---|---|
| 1 | ジョブ起動 | 終了コード2（COMPLETED_WITH_WARNING） |
| 2 | お知らせ状態 | 1→status='2'（処理済み）、2→status='9'（エラー） |
| 3 | `mail_send` | お知らせ1の対象のみ登録、お知らせ2の分はなし |
| 4 | 区域修正: お知らせ2の区域を13101へ修正→status='0'へ戻し再実行 | 終了コード0、お知らせ2も処理済み・対象登録 |

- **確認ポイント**: エラー化の局所性（他お知らせへの波及なし）、警告終了、修正後の完了。
- **実施結果**: OK
- **証跡**: exit=2 / ann1=2, ann2=9 / 修正後 exit=0・ann2=2

### ST-4: 異常終了（Skip上限超過）→ リラン

- **目的**: Skip 上限（10）超過で異常終了（1）すること。データ修正後に**同一 scheduledTime** でリスタートすると失敗Stepから再開して完走し、かつ Step2 で先に発生した区域展開不能の警告終了（2）が**リスタート後も維持される**こと（Job レベル ExecutionContext による警告集計の実機確認。設計レビュー由来の回帰観点）。
- **事前条件**: `reset.sql` → 区域不正のお知らせ2（99999）＋正常お知らせ1（13101）。お知らせ1の区域に、形式不正メールのユーザーを11件（Skip上限超過）＋正常1件を配置。

| # | 操作 | 期待結果 |
|---|---|---|
| 1 | ジョブ起動 | 終了コード1（FAILED）。ann2→status='9'、ann1→status='1'（処理中のまま） |
| 2 | データ修正（11件のメールを正しい形式へ） | - |
| 3 | **同一 scheduledTime かつ同一 errorFile** でリスタート | 終了コード2（COMPLETED_WITH_WARNING）。Step3 から再開（Step1/2は再実行されない）、区域警告が維持される |
| 4 | 結果 | ann1→status='2'、ann2→status='9'のまま、mail_send=12件 |

- **確認ポイント**: 異常終了→リラン完走、リスタート後の警告終了維持、冪等性。
- **実施結果**: OK
- **証跡**: 1回目 exit=1（skipCount=10でSkip上限超過、ann2→9）/ 2回目(restart, 同一instance) exit=2（COMPLETED_WITH_WARNING、Step3から再開）/ mail_send=12・ann1=2・ann2=9
- **補足**: 実施中、識別パラメータ（errorFile）を変えると別JobInstanceの新規実行になり区域警告が失われることを確認。運用手順書へ「リランは全識別パラメータを一致させる」ことを明記する必要がある（scenarios.md 冒頭の注記に反映済み）。

### ST-5: 二重起動防止

- **目的**: 同一ジョブの並行実行が基盤部品（DuplicateRunPreventingJobExecutionListener）で防止されること。
- **事前条件**: 性能データを流用し、全ユーザーを区域内にして対象10万件化（job1の処理時間を確保）。
  job1 を起動し、メタデータ（`batch.batch_job_execution.status='STARTED'`）で実行中を確認してから job2 を起動する。

| # | 操作 | 期待結果 |
|---|---|---|
| 1 | job1 を起動（バックグラウンド） | STARTED（実行中）になる |
| 2 | job1 実行中に job2 を別 scheduledTime で起動 | 2つ目が二重起動検知で失敗（終了コード1）、ログに「二重起動を検知しました」 |
| 3 | 結果 | job1 のみ完走（mail_send=100,000）。job2 は書込せず失敗 |

- **確認ポイント**: 2つ目の起動が基盤部品（DuplicateRunPreventingJobExecutionListener）で防止され、1つ目のデータ整合性が保たれること。
- **実施結果**: OK
- **証跡**: job2 exit=1・ログ「二重起動を検知しました: jobName=announcementNotifyJob 実行中executionIds=[18, 19]」／`SystemException: ...既に実行中のため起動を中止します（二重起動防止）`／job1 exit=0・mail_send=100,000
- **補足**: 2プロセスを完全同時起動すると、リスナーの実行中チェックが成立する前にメタデータ書込が競合し
  PostgreSQL のシリアライズ例外（`could not serialize access`）で片方が落ちる（多層防御としては同時実行を阻止できるが、
  意図した「二重起動検知」ログにはならない）。リスナーで確実に捕捉するには job1 の STARTED を確認してから job2 を起動する。

### ST-6: 本番相当データでの処理時間

- **目的**: ユーザー10万件・通知対象約3万件で、処理時間が起動間隔（15分）に十分収まること。チャンクサイズ調整の要否を判断する。
- **事前条件**: `reset.sql` → `generate_perf_data.sql`（本人27,000＋家族3,000＝対象30,000）。

| # | 操作 | 期待結果 |
|---|---|---|
| 1 | ジョブ起動（時間計測） | 終了コード0。処理時間が15分以内（十分な余裕） |
| 2 | `mail_send` 件数 | 30,000件（本人27,000＋家族3,000） |
| 3 | ログの件数 | Step3 の readCount=30,000, writeCount=30,000 |

- **確認ポイント**: 処理時間、対象件数の一致、抽出SQL（UNION）がインデックスを使えているか。
- **実施結果**: OK
- **証跡**: exit=0 / ジョブ全体 elapsedMs≒1,800（約1.8秒）、うち Step3 の read+write 30,000件が elapsedMs≒1,718 /
  mail_send=30,000（本人27,000＋家族3,000）/ commitCount=300（チャンク100×300）
- **評価**: 起動間隔15分（900秒）に対し約1.8秒と桁違いに余裕があり、チャンクサイズ調整・パーティショニングは不要。
  ローカル環境（Docker PostgreSQL・単一コネクション）での参考値であり、本番相当環境（Aurora）での実測は検証環境で別途行う。

### ST-7: 未処理0件での空振り実行

- **目的**: 未処理お知らせが無い状態でも正常終了（0件はエラーにしない）。15分ポーリングの空振り運用が安全であること。
- **事前条件**: `reset.sql`（全テーブル空）。

| # | 操作 | 期待結果 |
|---|---|---|
| 1 | ジョブ起動 | 終了コード0（COMPLETED）、mail_send=0件 |

- **確認ポイント**: 空振りが正常終了、例外・警告が出ないこと。
- **実施結果**: OK
- **証跡**: exit=0 / mail_send=0

## 実施サマリ・所見

- **実施日**: 2026-08-09（ローカル環境、プロファイル local）。全7シナリオ **合格**。バグ Issue の起票なし。
- **性能**: 対象30,000件で約1.8秒、10万件（ST-5）でも数秒。要件の件数規模では性能上の懸念なし。
- **運用手順書へ反映すべき所見（コード修正は不要）**:
  1. **リランは全識別パラメータ（`scheduledTime` と `errorFile`）を一致させる**こと。一方でも変えると
     別 JobInstance の新規実行となり、Step2 で先に flag 済みの区域展開不能（status=9）が再カウントされず
     警告終了が失われる（ST-4 で確認）。EventBridge/運用スクリプトのリラン手順で識別パラメータを固定化する。
  2. 二重起動の一次防御は EventBridge 側の同時実行抑止とする。アプリ内の
     `DuplicateRunPreventingJobExecutionListener` は多層防御であり、完全同時起動時はメタデータ書込の
     シリアライズ競合で阻止される（どちらの経路でも二重処理・二重通知は発生しない。ST-5 で確認）。
- **未実施（検証環境で別途）**: 本番相当環境（Aurora）での性能実測、EventBridge Scheduler からの終了コード連携、
  CloudWatch での構造化ログ・メトリクス確認（要件定義書 未確定 No.4 の処理時間制約は本結果で当面問題なしと判断）。
