# 要件定義書: お知らせ通知バッチ（announcement-notification）

| 項目 | 内容 |
|---|---|
| 案件名 | お知らせ通知バッチ（announcement-notification） |
| 作成日 / 更新日 | 2026-07-15 / 2026-07-15 |
| ステータス | 確定 |

## 1. 背景・目的

区域（都道府県・市町村レベル）を指定したお知らせ（防災情報・地域情報等）を、
該当区域に住むユーザーとその同居家族へメールで届けたい。
現状はお知らせと通知区域が業務システムから DB テーブルに登録されるのみで、
通知対象の抽出とメール送信依頼の作成が行われていない。
本バッチにより、未処理のお知らせから通知対象ユーザーを抽出し、
メール送信テーブルへの登録までを自動化する。

## 2. 業務フロー概要

1. 業務システムが業務イベント（お知らせ発信の都度）に応じて、お知らせと通知区域を DB テーブルへ登録する
2. **本バッチ**が未処理のお知らせを検出し、通知区域から通知対象ユーザーを抽出してメール送信テーブルへ登録する
3. 後続のメール送信基盤がメール送信テーブルを読み取り、実際のメール送信を行う（本バッチのスコープ外）

本バッチの責務は「通知対象の確定とメール送信依頼の登録」までであり、メールの実送信は行わない。

## 3. 機能要件

### 3.1 処理一覧

| No | 処理名 | 概要 | 入力 | 出力 |
|---|---|---|---|---|
| 1 | 未処理お知らせの取得 | 処理済み管理に基づき未処理のお知らせを抽出する | お知らせテーブル | （後続処理へ） |
| 2 | 通知区域の郵便番号展開 | 都道府県・市町村レベルの通知区域を郵便番号マスタで郵便番号リストへ展開する | 通知区域テーブル、郵便番号マスタ | （後続処理へ） |
| 3 | 通知対象ユーザーの抽出 | 住所の郵便番号が区域内のユーザー、およびその家族のうち区域内世帯の者を抽出し重複排除する | ユーザーテーブル、家族関係テーブル | （後続処理へ） |
| 4 | メール送信依頼の登録 | 通知対象ユーザーごとに送信依頼レコードを作成する | （No.3 の結果） | メール送信テーブル |
| 5 | お知らせの処理済み更新 | 処理を完了したお知らせを処理済みにする | （No.1 の結果） | お知らせテーブル |

※ ジョブ・Step への分割は基本設計の責務とし、ここでは処理の単位のみ定義する。

### 3.2 入力データ

| データ名 | 形式 | 文字コード | 件数規模 | 提供元 | 提供タイミング |
|---|---|---|---|---|---|
| お知らせ | DB テーブル | - | 1回あたり数件〜数十件想定 | 業務システム | 業務イベント発生の都度 |
| 通知区域 | DB テーブル（都道府県・市町村レベル。お知らせに紐づく） | - | お知らせあたり数件 | 業務システム | お知らせと同時 |
| ユーザー（参照） | DB テーブル（住所・郵便番号・メールアドレスを保持） | - | 数万〜数十万件 | 本システム | 常時 |
| 家族関係（参照） | DB テーブル（ユーザー間の家族関係を保持） | - | ユーザー数に比例 | 本システム | 常時 |
| 郵便番号マスタ（参照） | DB テーブル（都道府県・市町村 → 郵便番号の対応） | - | 全国で約12万件 | 未確定（未確定一覧 No.1） | 未確定 |

### 3.3 出力データ

| データ名 | 形式 | 出力先 | 利用者・後続処理 |
|---|---|---|---|
| メール送信依頼 | DB テーブル（通知対象ユーザーごとに1レコード） | メール送信テーブル | メール送信基盤（後続システム）が実送信 |

### 3.4 加工・変換ルール

- **区域の郵便番号展開**: 通知区域（都道府県・市町村）を郵便番号マスタと突合し、郵便番号のリストへ展開する。
  市町村指定の場合は当該市町村の全郵便番号、都道府県指定の場合は当該都道府県の全郵便番号を対象とする
- **通知対象の判定**:
  - 住所の郵便番号が展開後の郵便番号リストに完全一致するユーザーを対象とする
  - 上記対象ユーザーの家族（家族関係テーブルで紐づくユーザー）のうち、
    **区域内の世帯に住む者**のみを追加で対象とする（区域外に住む別居家族は対象外）。
    具体的には、住所（郵便番号）未登録のユーザーは区域内ユーザーと同居とみなして対象に含め、
    住所を持つユーザーは自身の住所のみで判定する
- **重複排除**: 同一お知らせ×同一ユーザーの組はメール送信依頼を1件のみ登録する
  （本人としても家族としても該当する場合、複数の家族関係から到達する場合を含む）

### 3.5 エラーデータの扱い

- 不正レコード（例: メールアドレスが不正な形式のユーザー）は
  **スキップして処理を継続**し、スキップ内容を記録する
- メールアドレス未設定のユーザーは通知不能のため**業務上の対象外**とする（エラー扱いにしない。
  2026-07-15 設計レビューにて確定）。郵便番号未設定のユーザーは家族ルールの判定対象であり不正ではない
- スキップが発生した場合、ジョブは終了コード 2（警告）で終了し、運用担当者が後日対応する
- 通知区域が郵便番号に展開できない（郵便番号マスタに該当がない）場合は、そのお知らせを
  エラー状態にして記録し、他のお知らせは処理を継続する（終了コード 2）。
  業務側で区域を修正のうえ未処理に戻して再実行する

## 4. 実行条件

| 項目 | 内容 |
|---|---|
| 実行タイミング | 随時。業務イベント契機（お知らせ・通知区域の DB 登録が契機）。起動方式は EventBridge Scheduler による15分間隔の定期ポーリング（処理済み管理により空振り実行も安全） |
| 先行ジョブ / 後続ジョブ | 先行: なし（業務システムによる契機データ登録が前提）/ 後続: メール送信基盤（別システム） |
| 処理時間の制約 | 未確定（未確定一覧 No.4） |
| 実行単位・パラメータ | 未処理のお知らせ全件を対象とする（処理済み管理により実行の都度、未処理分のみ処理） |

## 5. 非機能要件

| 項目 | 内容 |
|---|---|
| データ量（現在/将来） | ユーザー数万〜数十万件。1回の通知対象は区域規模に依存（最大で数十万件） |
| リラン要件 | お知らせ側の処理済み管理により、失敗時は再実行すれば未処理分のみが処理される（同一ユーザーへの二重登録なし）。Step 途中からの再開（リスタート）は必須としない |
| 監視・通知 | 終了コードによる監視（0=正常 / 2=警告 / 1=異常）。詳細な通知先・検知方法は運用設計に従う |
| データ保持・退避 | 入力はすべて DB のため退避なし。スキップ記録の保持期間は運用設計に従う |
| セキュリティ（個人情報等） | 住所・メールアドレス等の個人情報を扱う。ログへの個人情報出力禁止 |
